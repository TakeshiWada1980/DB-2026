## 正規化 (概要)

データベース設計における **正規化** (Normalization) とは、<u>データの冗長性を減らし、整合性を維持しやすいテーブル構造</u>にするための概念、および、その具体的な作業を意味します。これは、**無損失分解** を前提に、**1事実1箇所** (1 fact in 1 place) という考え方に基づきテーブルを分解・整理していく作業になります。そして、その結果として得られるテーブル構造を **_正規形_** (Normal Form) と呼びます。

- **正規化** (Normalization) と **正規形** (Normal Form) という言葉の使い分けに注意してください。

::: {.balloon .char-01 .face-02 .tone-yellow}
**無損失分解** とは、テーブルを複数に分解しても、それらを結合することで、元の情報を完全に復元できるような分解を意味します。

**「1事実1箇所」**とは、ある事実に関する情報は、原則として1箇所に記録し、複数の場所で重複して管理しないという考え方です。同じ情報をあちこちに記録すると、変更が生じた際にすべての箇所を更新する必要があり、更新漏れによるデータの不整合が発生しやすくなります。
:::

正規形には、いくつかの段階 (レベル) があります。非正規形からはじまり、第1正規形、第2正規形、第3正規形、ボイス・コッド正規形 (第3.5正規形)、第4正規形、第5正規形 へと整理していきます。ただし、実務上は <span class="masked">第3正規形</span> までで十分とされることが多く、本科目でも「**第3正規形**」までを扱います。

なお、第1正規形 (First Normal Form) は「**1NF**」のように略表記されることがあるので覚えておいてください。同様に **2NF**、**3NF**... と表現されます。

整理すると以下のようになります。以降、これらについて、具体例を示しながら詳しく理解を深めていきます。

- **非正規形**： 非スカラー値を含むカラムが存在するか、列方向に同種のデータが繰り返されている。
- **第1正規形 (1NF)**： 各カラムがスカラー値のみを格納し、列方向の繰り返しが排除されている。
- **第2正規形 (2NF)**： 第1正規形の要件を満たし、複合主キーの一部に対する **部分関数従属** が排除されている。
- **第3正規形 (3NF)**： 第2正規形の要件を満たし、非キー属性同士の **推移的関数従属** も排除されている。

## 非正規形

**非スカラー値** (＝複合値、つまり、複数の値を組み合わせたもの) を含むカラムが存在したり、**列方向に同種のデータが繰り返されていたりする構造**のテーブルは、**非正規形** (＝第1正規形 (1NF) を満たしていない状態) とよばれます。

たとえば、次のようなテーブルは、典型的な **非正規形** (Unnormalized Form) となります。テーブル上で、主キーは <u>下線</u> で示しています。


**▼ 非正規形テーブル1** (スキル管理テーブル)

|<u>character_id</u>|name|job|skill|
|:--:|:--|:--|:--|
|1|Alice|Priest|Heal, Resurrection|
|2|Bob|Monk|DragonKick|
|3|Charlie|Wizard|Fire, Thunder, Venom|
|4|Ellen|Wizard|Thunder|

**▼ 非正規形テーブル2** (所持アイテム管理テーブル)

|<u>character_id</u>|name|item1|qty1|item2|qty2|item3|qty3|
|:--:|:--|:--|:--:|:--|:--:|:--|:--:|
|1|Alice|Map|1|Potion|5| ||
|2|Bob|Ring|3||| ||
|3|Charlie|Wand+1|1|Scroll|4|Potion|3|
|4|Ellen|||||||

::: {.balloon .char-01 .face-05 .tone-blue}
**qty** は <span class="masked">quantity (数量)</span> の略表記です。

略語としてよく使用されるので覚えておいてください。
:::


**非正規形テーブル1** は、**skill** カラムに<span class="masked">非スカラー値 (複合値)</span> を含んでいます。このようなテーブル設計では、個々のスキルを独立したデータとして扱うことが難しくなり、**検索や更新が煩雑になります**。

::: {.balloon .char-01 .face-04 .tone-blue}
たとえば「<u>スキルとして **Heal** を使えるキャラクタを検索したい</u>」という単純な問い合わせでも、[LIKE述語](lecture04.html#like述語-like条件パターンマッチ演算子) を使用した **部分一致検索** (`WHERE skill LIKE '%Heal%'`) などが必要になります。しかも、この方法では `SuperHeal` なども検索結果に含まれる可能性があるため、検索の正確性や処理性能に注意が必要となってきます。

- `LIKE '%Heal%'` のような部分一致検索では、通常のインデックスを利用した効率的な検索が難しく、大量のデータを扱う場合には性能面で問題になることがあります。なお、インデックスについては今後の授業で扱います。
:::

<div class="note type-tips">
**カラムに複合値を入れると検索精度や更新容易性が損なわれる理由**

単純な部分一致検索 `LIKE '%Heal%'` では <span class="masked">MegaHeal や HealBlock</span> のように、名前の一部に Heal を含むスキルを含むレコードを抽出してしまう可能性があります。

また、スキルの一部だけを更新したい場合 (たとえば `Fire, Thunder, Venom` に `Quake` を追加するような処理) に、**文字列の部分編集や置換操作**が必要となります。
</div>


また、**非正規形テーブル2** では、<span class="masked">同じ種類の情報 (アイテムとその数量) が列方向に繰り返されています</span>。これも、第1正規形 (1NF) を満たしていない典型的なパターンとなります。

このようなテーブル設計では「**所持可能なアイテムを3種類から4種類に増やしたい**」といった仕様変更のたびに <span class="masked">新しいカラムの追加 (＝テーブルスキーマの変更)</span> が必要になるという問題があります。

:::{.note .type-tips}

**「レコードの追加」と「カラムの追加」は何が違うのか**

RDBにおいて、`INSERT` による「レコードの追加」や `DELETE` による「レコードの削除」は **DML操作** に分類され、テーブルの構造を変更せずに実行できます。一方で「カラムの追加・削除」は `ALTER TABLE` を用いた **DDL操作** に分類され、テーブルの構造そのもの (＝テーブルスキーマ) を変更する処理となります。

DDL操作は、変更内容によっては処理に非常に長い時間がかかることがあります。また、スキーマを変更すると、**既存の SQL が参照しているカラム名やテーブル構造との不整合が生じて**、これまでの SQL や アプリが正常に動作しなくなる可能性もあるため、極めて慎重に実行する必要があります。

このため、運用開始後にデータが増加するたびにカラムを追加しなければならないようなテーブル設計は、できるだけ避けることが重要となります。
:::

また、**非正規形テーブル2** のようなテーブル構造では、大多数のキャラクタがアイテムを1種類しか所持していない場合、<span class="masked">多くのカラムが `NULL` となり、無駄の多いテーブル構造</span> になります。さらに、`SUM()` や `COUNT()` を使った集計処理でも、複数のカラムを横断して扱う必要があるため、**SQL文が複雑になり、保守性や処理性能の面でも問題が生じやすくなります**。


::: {.balloon .char-01 .face-04 .tone-blue}

たとえば、**非正規形テーブル2** で各キャラクタが所持しているアイテムの総数を求めるには、次のような SQL 文が必要になります。

```sql{.numberLines caption="アイテム所持数の集計"}
SELECT
  name,
  COALESCE(qty1, 0) 
  + COALESCE(qty2, 0) 
  + COALESCE(qty3, 0) AS "所持アイテム総数"
FROM 
  characters;
```

ここで、所持可能なアイテムの種類が「32種類」に増えた場合を考えてみてください。集計するカラムも32個に増えるため、SQL文が長く複雑になり、保守が難しくなることが分かると思います。
:::

## 第1正規化

第1正規化、つまり、**非正規形のテーブルを第1正規形に整える**には、**複合値や列方向 (横方向) に繰り返されている情報**を <span class="masked">行方向 (縦方向) に展開して保持する</span> ようにします。

具体的には、以下のようにします。

**▼ 先ほどの 非正規形テーブル1 (スキル管理テーブル) を第1正規化したテーブル**

|<u>character_id</u>|name|job|skill|

|1|Alice|Priest|Resurrection|

|3|Charlie|Wizard|Thunder|
|3|Charlie|Wizard|Venom|
|4|Ellen|Wizard|Thunder|


これにより、第1正規形の要件である「<u>各カラムにはスカラー値のみを格納し、列方向の繰り返しが排除されている</u>」を満たした構造となりました。

## 第2正規化

第1正規形の要件を満たし、<u>複合主キーの一部に対する **部分関数従属** が排除</u> された構造を **_第2正規形_** といいます。

まずは、第2正規化を理解するうえで重要となる **関数従属** という概念について解説し、その後、第2正規化の具体的な方法を説明します。なお、「関数従属」は資格試験などでも頻出する重要な用語なので、しっかりと理解しておいてください。

### 関数従属

**関数従属** (**FD: Functional Dependency**) とは...

> ある属性集合 $\mathrm{X}$ の値が決まると、別の属性集合 $\mathrm{Y}$ の値も一意に定まる

...という「**属性間の関係を表す概念**」になります。このような関係が成立するとき、「<u>$\mathrm{Y}$ は $\mathrm{X}$ に関数従属する</u>」といい、記号では「 $\mathrm{X}\rightarrow\mathrm{Y}$ 」のように表現します。

::: {.balloon .char-01 .face-05 .tone-blue}
たとえば、$\mathrm{X}=\{x_1,\ x_2\}$、$\mathrm{Y}=\{y_1,\ y_2,\ y_3\}$ の場合は、次のように表現します。

$$
\{x_1,\ x_2\}\rightarrow\{y_1,\ y_2,\ y_3\}
$$
:::

RDB のテーブル設計では、**「あるカラム集合 $\mathrm{X}$ の値」が決まると「別のカラム集合 $\mathrm{Y}$ の値」も一意に決まる関係** を「<font color="deeppink">$\mathrm{Y}$ <b>は</b> $\mathrm{X}$ <b>に関数従属する</b></font>」といいます。

- 具体的には、**同じ $\mathrm{X}$ の値を持つレコードが複数存在する場合、それらのレコードでは $\mathrm{Y}$ の値も必ず同じになる** ということです。このような関係を「<u>$\mathrm{Y}$ は $\mathrm{X}$ に関数従属する</u>」といい、単に「<u>$\mathrm{Y}$ は $\mathrm{X}$ に従属する</u>」という場合もあります。
- あとで詳しく解説しますが、関数従属には「**部分**関数従属」や「**推移的**関数従属」といった概念もあります。

#### 具体例で関数従属を理解する

たとえば、キャラクタの情報を管理する次のテーブルを考えます。各キャラクタには固有の **character_id** を割り当て、1キャラクタにつき1行を登録します。また、同じ職業ID (**job_id**) には、常に同じ職業名 (**job**) が対応するものとします。

|character_id|name|job_id|job|level|guild|
|:--:|:--:|:--:|:--:|:--:|:--:|
|1|Alice|J5|Priest|42|Yamato|
|2|Bob|J2|Monk|33|hameln|
|3|Charlie|J6|Wizard|57||
|4|Ellen|J6|Wizard|51||

このとき、次のような **関数従属** が成立します。

- **character_id** が決まれば、**name**、**job_id**、**job**、**level**、**guild** の値も一意に決まるので...
  - **name**, **job_id**, **job**, **level**, **guild** は、**character_id** に **<u>関数従属</u>** する
  - <span class="masked">$\{\mathrm{character\_id}\} \rightarrow \{\mathrm{name},\ \mathrm{job\_id},\ \mathrm{job},\ \mathrm{level},\ \mathrm{guild}\}$</span>
- **job_id** が決まれば、**job** の値も一意に決まるので...
  - **job** は、**job_id** に **<u>関数従属</u>** する
  - <span class="masked">$\{\mathrm{job\_id}\} \rightarrow \{\mathrm{job}\}$</span>

::: {.balloon .char-01 .face-01 .tone-pink}

なお、テーブルに格納されている<u>**現時点のレコードだけに着目**</u>すると...

> character_id、name、job_id、job、guild は、level に関数従属する

...と判断できそうですが、**これは誤りです**。

なぜなら、現在のテーブルでは **level** の値がすべて異なっており、**たまたま level の値から各レコードを一意に特定できているだけ**だからです。

:::

正規化における関数従属とは、**すべての有効なデータ状態において常に成立する制約** を意味します。そのため「<u>現時点のデータでは、たまたま成立しているだけの関係</u>」は、関数従属とは見なしません。

このように、関数従属の判断には、現時点のデータだけでなく、<span class="masked">ビジネスルールやドメイン知識（対象とする業務や世界に関する知識）に基づく分析</span> が必要となります。

RDB のテーブル設計では、基本的に <span class="masked">「主キー以外のすべてのカラム」が「主キー」に関数従属</span> するように設計します。

ただし、**主キーに関数従属しているだけでは、第2正規形の要件を満たすとは限りません**。特に、主キーが複数のカラムから構成される「複合主キー」の場合、その一部のカラムだけで値が決まる「部分関数従属」が存在する可能性があります。

::: {.balloon .char-01 .face-05 .tone-blue}
たとえば、「学生ID」と「科目ID」の組み合わせを「複合主キー」とするテーブルにおいて、「学生名」が「学生ID」だけで一意に決まる場合がこれに該当します。このように、複合主キーの一部だけで、主キー以外のカラムの値が決まる関係を「**部分関数従属**」といいます。
:::

そこで、「第2正規化」では、<u>複合主キーの一部に対する **部分関数従属** を排除</u>し、主キー以外のすべてのカラムが、主キー全体に **完全関数従属** する構造を目指します。

:::prompts

- RDBにおいて、関数従属であるかは、レコードのサンプルで判断するだけではなく、ドメイン知識に基づいて判断するべきであると説明されました。そもそも「ドメイン知識」とはなんですか。

:::

#### 定着確認

- RDB において、id が決まれば name、age、address が一意に決まるとき、その関係を適切に表現しているのは「name, age, address は id に関数従属する」と「id は name, age, address に関数従属する」のどちらか。「前者」または「後者」で答えよ。
  - **答え** : <span class="masked">前者</span> 
- RDB において、id が決まれば name、age、address が一意に決まるとき、この関係を関数従属を示す記号で表せ。
  - **答え** : <span class="masked">$\{$ id $\} \rightarrow \{$ name, age, address $\}$ </span> 
- 関数従属は「データの偶然の並び」によって判断するのではなく、属性間の意味的な結びつき (制約) として常に成り立つ関係として考えるべきである。この説明は「適切である」か「適切ではない」か答えよ。
  - **答え** : <span class="masked">適切である</span> 

- 「$\mathrm{Y}$ は $\mathrm{X}$ に関数従属する」とき、同じ $\mathrm{X}$ の値を持つレコードが複数あってもよいか。「$\mathrm{Y}$ の値が一意に決まる」とは何を意味するかを踏まえて答えよ。
  - **答え** : <span class="masked">複数あってもよい。「$\mathrm{Y}$ の値が一意に決まる」とは、同じ $\mathrm{X}$ の値を持つレコードでは、$\mathrm{Y}$ の値がすべて同じになるという意味です。</span>

### 「部分関数従属」と「完全関数従属」

RDB において、**テーブルの主キーが複数のカラムから構成される場合**（つまり、複合主キーである場合）、**主キーを構成するカラムの「一部だけに関数従属するカラム」が存在することがあります**。

たとえば、次のようなテーブルがあるとします。

|<u>character_id</u>|name|<u>item_id</u>|item|qty|
|:--:|:--|:--:|:--|:--:|
|1|Alice|1|Map|1|
|1|Alice|2|Potion|5|
|2|Bob|3|Ring|3|
|3|Charlie|4|Wand+1|1|
|3|Charlie|5|Scroll|4|
|3|Charlie|2|Potion|3|
|4|Ellen||||

このテーブルでは、**character_id** と **item_id** の組み合わせが複合主キーとなっています。しかし、次のように **複合主キーの「一部だけ」で値が決まるカラム** が存在しています。

- **item** カラムは、**item_id だけ** に関数従属しています。
  - **item_id** の値だけで **item** の値が一意に決まり、**character_id** の値には依存しません。
- **name** カラムは、**character_id だけ** に関数従属しています。
  - **character_id** の値だけで **name** の値が一意に決まり、**item_id** の値には依存しません。

このように、**複合主キーの一部だけに関数従属する関係** を **_部分関数従属_**（PFD: Partial Functional Dependency）といいます。一方、<u>複合主キーを構成するすべてのカラムがそろって、はじめて値が一意に決まる関係</u>を **_完全関数従属_**（FFD: Full Functional Dependency）といいます。

::: {.balloon .char-01 .face-02 .tone-yellow}
たとえば、上記のテーブルにおいて、<span class="masked">qty</span> カラムの値は、**character_id** と **item_id** の両方がそろわなければ一意に決まりません。これは、同じアイテムであっても、キャラクタによって所持数が異なる可能性があるためです。

このような関係を「**qty は character_id と item_id の組み合わせに完全関数従属する**」といいます。
:::

::: {.note .type-senior}
**中級者向け**

「第2正規形」の厳密な判定では、主キーだけでなく「候補キー」も考慮する必要があります。そのため、[サロゲートキー](lecture06.html#nameカラムを主キーにできるか)を単独の主キーとして設定していても、別に複数カラムからなる候補キーが存在する場合には、部分関数従属が残っている可能性があります。

:::

#### 定着確認

- 「$\mathrm{Y}$ は $\mathrm{X}$ に関数従属する」という説明だけで、部分関数従属か完全関数従属かを「判断できる」か「判断できない」かを答えよ。

  - **答え**: <span class="masked">満たしている</span>
- **title** カラムは、この複合主キーに対して「部分関数従属」しているか、「完全関数従属」しているかを答えよ。
  - **答え**: <span class="masked">部分関数従属</span>

  - **答え**: <span class="masked">部分関数従属</span>

### 第2正規形

**第2正規化** では、第1正規形の要件を満たしたうえで、**複合主キーの一部に対する部分関数従属を排除**し、主キー以外のカラムが主キー全体に <span class="masked">完全関数従属</span> するようにテーブルを分解していきます。

たとえば、次のような部分関数従属を含むテーブルがあるとします。

**▼ 第1正規形（第2正規形ではない）**

|<u>character_id</u>|name|<u>item_id</u>|item|qty|
|:--:|:--|:--:|:--|:--:|
|1|Alice|1|Map|1|
|1|Alice|2|Potion|5|
|2|Bob|3|Ring|3|
|3|Charlie|4|Wand+1|1|
|3|Charlie|5|Scroll|4|
|3|Charlie|2|Potion|3|
|4|Ellen||||

このテーブルに存在する **部分関数従属を排除し、第2正規形の要件を満たすように分解すると、次の3つのテーブルになります**。なお、一部のカラム名は分解後の構造にあわせて変更しています。

**▼ characters テーブル (第2正規形)**

|<u>character_id</u>|name|
|:--:|:--|
|1|Alice|
|2|Bob|
|3|Charlie|
|4|Ellen|

**▼ items テーブル (第2正規形)**

|<u>item_id</u>|name|
|:--:|:--|
|1|Map|
|2|Potion|
|3|Ring|
|4|Wand+1|

**▼ character_items テーブル (第2正規形・複合主キー・完全関数従属)**

|<u>character_id</u><br>(FK)|<u>item_id</u><br>(FK)|qty|
|:--:|:--:|:--:|
|1|1|1|
|1|2|5|
|2|3|3|
|3|4|1|

- **FK** は、外部キー (＝<span class="masked">他のテーブルの主キーを参照するカラム</span>) であることを表しています。

::: {.balloon .char-01 .face-02 .tone-yellow}
分解後の **characters** テーブルと **items** テーブルでは、それぞれの主キーによって **name** が一意に決まる構造になっています。また、**character_items** テーブルでは、**qty** が **character_id** と **item_id** の組み合わせに「完全関数従属」しています。

これにより、すべての部分関数従属が解消され、3つのテーブルはいずれも「第2正規形」の要件を満たしているといえます。
:::

ここで注目したいのは、この分解結果が、前回講義で学んだ [多対多のリレーションの分割（中間テーブル化）](lecture06.html#多対多のリレーションの分割-中間テーブル化) と同じ構造になっていることです。

これは、**「多対多」の関係を中間テーブルで適切に表現することが、部分関数従属の解消にもつながるため**です。このように、論理ER図を適切に設計していれば、結果として自然に「第2正規形」の要件を満たすようなテーブル構造になっていることも少なくありません。

![img](figs/07/LER-04-1.png)

::: {.balloon .char-01 .face-05 .tone-blue}
このようなこともあるので、DB設計では、いきなりテーブルを作成するのではなく、**事前に「論理ER図」を描いて、データの構造や関係を整理しておくことが重要です**。そうすることで、後から正規化のためにテーブルを分解・修正する手間も減らすことができます。
:::

## 第3正規化

**第3正規化** では、第2正規形の要件を満たしつつ、**非キー属性を経由する「推移的関数従属」**というものを排除していきます。非キー属性とは <span class="masked">主キーを構成しないカラム、つまり「主キー以外のカラム」</span> を指します。

### 推移的関数従属

**_推移的関数従属_** (TFD: Transitive Functional Dependency) とは、**主キーから別のカラムを経由して、さらに別のカラムの値が決まる関係** を指します。

具体的には、**$\{$ 主キー $\} \rightarrow \{$ 非キーA $\} \rightarrow \{$ 非キーB $\}$** という依存の連鎖がある場合「**非キー B は、主キーに推移的に関数従属している**」と表現します。

::: {.balloon .char-01 .face-05 .tone-blue}
簡単にいえば、**「A が決まれば B が決まり、B が決まれば C も決まる」という芋づる式の関係**を指します。「主キー」から直接考えるのではなく、途中のカラムをたどることで、別のカラムの値まで決まってしまうような関係を「推移的関数従属」といいます。
:::


たとえば、次のようなテーブルを考えます。このテーブルの「主キー」は、<u>下線</u> で示した **character_id** であり、「**非キー属性**」は <span class="masked">name、job_id、job_name</span> となります。このテーブルは、次の理由から「第2正規形」までの要件を満たしています。

- 各カラムには「スカラー値」が格納され、列方向の繰り返しもないため、**第1正規形** の要件を満たしています。
- 主キーは単一のカラムで構成されており、その一部に対する「部分関数従属」は存在しないため、**第2正規形** の要件も満たしています。

|<u>character_id</u>|name|job_id|job_name|
|:--:|:--|:--:|:--|
|1|Alice|J5|Priest|
|2|Bob|J2|Monk|
|3|Charlie|J6|Wizard|
|4|Ellen|J6|Wizard|

::: {.balloon .char-01 .face-02 .tone-yellow}

このテーブルにおいて、「**推移的関数従属**」の観点から注目すべき点は、次の 2 つです。

- 主キーである **character_id** が決まれば、**job_id** の値が一意に決まる。
- 非キー属性である **job_id** が決まれば、**job_name** の値も一意に決まる。

つまり、**$\{$ character_id $\} \rightarrow \{$ job_id $\} \rightarrow \{$ job_name $\}$** という依存関係が成立しています。
:::


この関係では、主キーである **character_id** から **job_name** の値も一意に決まりますが、**job_name は、主キー以外の job_id によっても一意に決まる** という点が重要です。

このように、主キーから非キー属性を経由して別の非キー属性が決まる関係を「**job_name は、主キーに推移的に関数従属している**」といいます。

そして、このような **「推移的関数従属」を排除するようにテーブルを分解する操作** が「**第3正規化**」となります。

### 第3正規形

次のような**推移的関数従属を含むテーブル** (＝具体的には <span class="masked">$\{$ character_id $\} \rightarrow \{$ job_id $\} \rightarrow \{$ job_name $\}$</span> ) があるとします。

|<u>character_id</u>|name|job_id|job_name|
|:--:|:--|:--:|:--|
|1|Alice|J5|Priest|
|2|Bob|J2|Monk|
|3|Charlie|J6|Wizard|
|4|Ellen|J6|Wizard|

このテーブルは「推移的関数従属」を解消することで、次の2つのテーブル (**characters** と **jobs**) に分解できます。これにより、両方のテーブルが「第3正規形」の要件を満たす構造になります。

**▼ characters テーブル (第3正規形)**

|<u>character_id</u>|name|job_id (FK)|
|:--:|:--|:--:|
|1|Alice|J5|
|2|Bob|J2|
|3|Charlie|J6|
|4|Ellen|J6|

**▼ jobs テーブル (第3正規形)**

|<u>job_id</u>|name|
|:--:|:--|
|J1|Fighter|
|J2|Monk|
|J3|Ninja|
|J4|Samurai|
|J5|Priest|
|J6|Wizard|

分解前のテーブルにあった `Monk`、`Priest`、`Wizard` に加え、分解後に、どのキャラクタも就いていない `Fighter`、`Ninja`、`Samurai` を登録した例です。

---

::: {.balloon .char-01 .face-05 .tone-blue}
分解前のテーブルでは、そのジョブに就いているキャラクタが存在しない場合、ジョブの情報だけを登録することができませんでした。一方、分解後は **jobs** テーブルでジョブ情報を独立して管理できるため、キャラクタの有無にかかわらず、すべてのジョブを登録・保持できるようになりました。

## 物理設計 (基礎)

これまでの論理設計では、**テーブルの構成やテーブル間の関係** を設計してきました。これに対して、**物理設計 (Physical Design)** では、PostgreSQL や MySQL などの具体的な RDBMS を前提に、**論理設計で決めた構造を実装するための具体的な仕様** について決定していきます。

::: {.balloon .char-01 .face-05 .tone-blue}
具体的には、**データ型の選定**、**主キー／外部キー／CHECK 制約などの設定**、`CREATE TABLE` 文などの DDL による **テーブル定義**、検索性能を高めるための **インデックス設計**といったことが物理設計の内容となります。
:::

さらに、データベースを安定的かつ効率的に運用するためには、ストレージやメモリなどのハードウェア構成、RAID による冗長化、バックアップ、レプリケーション、負荷分散なども検討する必要があります。これらも物理設計の範疇であり、インフラ設計や運用設計とも密接に関係するものとなります。

ここからは、論理設計で決定したテーブル構造をもとに、PostgreSQL 18 を使って実際にテーブルを作成していきます。特に、各カラムの「データ型」「主キー」「非NULL制約」 の指定方法について詳しく取り上げていきます。

::: prompts
- データベースの「レプリケーション」は、どのような目的で利用される仕組みですか。「バックアップ」との違いも含めて説明してください。
- コンピュータストレージの文脈において「RAID」とは何ですか。2年前の「情報2」の授業で習ったのですが完全に内容を忘れてしまいました。
:::

#### 定着確認

- RDBの設計において、テーブル間の関係や主キー、外部キーを決定した後、使用する RDBMS の仕様に合わせて、各カラムのデータ型や制約の定義方法、インデックスの構成などを具体化する設計段階を何とよぶか。「概念設計」「論理設計」「物理設計」から選んで答えよ。
  - **答え**：<span class="masked">物理設計</span>
- 次のうち、データベースの「物理設計」で行なう作業として、<u>最も適切でないもの</u>を1つ選び、番号で答えよ。
  1. 検索処理を効率化するために、インデックスを設計する。

  2. ユースケース図の作成

### 第07回の演習用スキーマ

今回の演習では、これまで使用してきたデータベース **playground** 内に、第07回以降の SQL 演習で使用する **w07** という新しいスキーマを作成します。

::: {.balloon .char-01 .face-05 .tone-blue}
スキーマが異なっていれば、テーブル名が同じでも別々のテーブルとして扱われます。例えば、`w07.characters` と `w03.characters` は、それぞれ独立したテーブルとなります。

なお、第03回講義で解説したように、RDB において [「スキーマ」という用語は異なる 2 つの意味がある](lecture03.html#rdbms-におけるスキーマという用語の2つの意味) ので注意してください。
:::

**w07** スキーマを作成するために **from-teacher/07/setup.sql** を実行してください。このファイルには、以下のような SQL 文が記述されています。

```sql{.numberLines caption="from-teacher/07/setup.sql（スキーマ w07 の作成）"}
CREATE SCHEMA IF NOT EXISTS w07;

SET
  search_path TO w07;
```

```sql{.numberLines caption="CREATEによるテーブルの作成"}
  search_path TO w07;

-- 既に存在するなら削除

-- テーブルの作成

  character_id INTEGER PRIMARY KEY, -- 整数型、PK

  last_login_at TIMESTAMP           -- 日時型(タイムゾーンなし)

    6,
```

### データ型

PostgreSQL で利用可能な **代表的なデータ型** として、次のようなものがあります。

- `INTEGER`: -2,147,483,648 から +2,147,483,647 までの範囲の整数値を格納可能な型です。PostgreSQL では `INT` という省略形の表記も可能です。
  - より小さな範囲の整数を格納可能な `SMALLINT`、より大きな範囲の整数を格納可能な `BIGINT` もあります。
- `TEXT`: **長さの上限を指定せずに使用する可変長文字列型**です。PostgreSQL で1つの文字列に格納できる大きさは、最大で約 1GB となります。空文字 (長さ0の文字列) と `NULL` は区別されます。
- `VARCHAR(n)`: **最大n文字までを格納可能な可変長文字列型**です。`TEXT` 型と同様、空文字と `NULL` は異なる値として扱われます。
  - `n` の単位は <span class="masked">バイト数ではなく、文字数</span> です。たとえば、`VARCHAR(16)` には、英語でも日本語でも「16文字」まで格納できます。
- `NUMERIC(n, m)`: **数値を正確に保持する型**です。`n` は数値全体の桁数、`m` は小数点以下の桁数を指定します (ここでは `m` は0以上とします)。
  - 第03回の `w03.characters` テーブルでも、`buff` に `NUMERIC(3, 2)` を使用しています。
  - たとえば、`NUMERIC(6, 2)` は -9,999.99 から +9,999.99 までの値を小数点以下2桁で正確に保持できます。小数部が 2 桁を超える入力値は丸められ、<span class="masked">丸めた結果が範囲を超えるとエラー</span> になります。
  - 単に `NUMERIC` だけを指定すると、型として桁数や小数点以下の桁数を固定せず、PostgreSQL が扱える範囲で数値を格納できます。
  - PostgreSQL では、`DECIMAL` は `NUMERIC` の別名となります。
- `BOOLEAN`: 真偽値を扱うブール型です。`TRUE` または `FALSE` を格納します。`NULL` を許すカラムでは、値が不明な状態も表せます。
- `DATE`: 日付型です。年、月、日の情報だけを保持し、時刻やタイムゾーンの情報は含みません。
- `TIMESTAMP`: 日付と時刻を <span class="masked">タイムゾーンなし</span> で扱う型になります。時刻は、100万分の1秒 (マイクロ秒) までの精度で保持されます。
  - タイムゾーンを考慮して特定の時点を扱う場合は `TIMESTAMPTZ` を使用します。入力された日時は UTC に換算して保存され、表示時は接続のタイムゾーンに変換されます。タイムゾーン情報そのものを保存する型ではなく、特定の時点を表す値を保存し、接続のタイムゾーン設定に応じた日時として表示する型と言えます。

::: {.balloon .char-01 .face-02 .tone-yellow}

PostgreSQL では、配列や JSON の値を格納するカラムを定義することもできます。JSON を扱う型には `JSON` と `JSONB` があり、`JSON` は入力されたテキストをそのまま保持し、`JSONB` は解析したデータをバイナリ形式で保持します。

ただし、本講義のなかでは、整数、文字列、日付など、上記に示したような**基本的なデータ型のみ**を使用します。
:::

:::{.note .type-senior}

**中級者向け： NUMERIC 型で負の桁数を指定する**

PostgreSQL 15 以降では、`NUMERIC(n, m)` の **`m` に負の整数を指定することができます**。通常、`m` は小数点以下の桁数を表しますが、負の値を指定すると、小数点より左側の桁で <span class="masked">数値を丸めること</span> ができます。

例えば、`NUMERIC(5, -2)` では、数値を「100」の位に丸めて保存します。

| 保存する値 | 実際に保存される値 |
|---|---|
| 12345 | 12300 |
| 12367 | 12400 |
| 12350 | 12400 |
| 9876543 | 9876500 |
| 9999950 | エラー (丸めると 10000000 になり、桁数を超える) |

このように、負の `m` は、細かい数値を扱う必要がなく、100 単位や 1000 単位などで数値を管理したい場合に利用できます。なお、**SQL標準では `m` に負の数を指定することは認められていません**。これは PostgreSQL 独自の拡張機能であるため、ほかの RDBMS との互換性には注意が必要です。
:::

### 非NULL制約（NOT NULL制約）

特定のカラムに <span class="masked">`NULL`</span> を格納できないようにするには、`CREATE TABLE` 文で「**非NULL制約**」を指定します。

たとえば、`is_online BOOLEAN NOT NULL` と記述すると、`is_online` カラムには `TRUE` または `FALSE` のいずれかを必ず登録する必要があり、`NULL` は登録できなくなります。

- 「**非NULL制約**」は「**NOT NULL制約**」とも呼ばれます。
- `character_id INTEGER PRIMARY KEY` のように、主キーに指定されたカラムには、**非NULL制約とUNIQUE制約に相当する制約**が自動的に適用されます。
  - `NOT NULL` や `UNIQUE` を明記しなくても、主キーには `NULL` や重複する値を登録できません。


### PRIMARY KEY指定

`CREATE TABLE` 文において、主キー (PK) は `PRIMARY KEY` キーワードを使用して指定します。

たとえば、次のようにすることで `character_id` を主キーに指定することができます。このような指定方法を「**カラムレベルの主キー指定**」といいます。

```sql{.numberLines caption="主キーの設定(1)"}
CREATE TABLE w07.character_profiles (
  character_id INTEGER PRIMARY KEY,
  name VARCHAR(16) NOT NULL
);
```

また、次のように <span class="masked">テーブル定義の末尾</span> に主キーの指定を記述することもできます。このような形式を「**テーブルレベルの主キー指定**」といいます。

```sql{.numberLines caption="主キーの設定(2)"}
CREATE TABLE w07.character_profiles (
  character_id INTEGER,
  name VARCHAR(16) NOT NULL,
  PRIMARY KEY (character_id)
);
```

前回講義で扱った [複合主キー](lecture06.html#複合主キー) については、テーブルレベルの主キー指定を用いて次のように記述します。

```sql{.numberLines caption="複合主キーの設定(2)"}
CREATE TABLE w07.character_items (
  character_id INTEGER,
  item_id INTEGER,
  quantity INTEGER NOT NULL,
  PRIMARY KEY (character_id, item_id)
);
```

ここで、複合主キーを構成する **character_id** と **item_id** については、どちらにも `NULL` を登録できなくなります。また、主キーの制約によって、**character_id** と **item_id** の**組み合わせの重複が禁止**されるようになります。

::: {.balloon .char-01 .face-02 .tone-yellow}
たとえば、Alice (**character_id = 1**) が回復薬 (**item_id = 38**) を 3 個持っていて、敵を倒して回復薬をもう1個手に入れたとします。

所持アイテムのテーブルには、すでに **(character_id, item_id, quantity) = (1, 38, 3)** の行が登録されています。

このとき、手に入れた 1 個を次のように `INSERT` すると、複合主キーの組み合わせ **(1, 38)** が重複するため、エラーになります。

```sql{.numberLines caption="INSERT"}
INSERT INTO w07.character_items (character_id, item_id, quantity)
VALUES (1, 38, 1);
```

この場合は、`UPDATE` 文で Alice の回復薬を管理する行を選び、**quantity** を 1 増やす必要があります。

```sql{.numberLines caption="UPDATE"}
UPDATE w07.character_items
SET quantity = quantity + 1
WHERE character_id = 1 AND item_id = 38;
```

`WHERE` で2つのIDを指定することで、Alice の回復薬の所持数だけが3個から4個に変わります。
:::
