## データベースの設計

ここまでの講義では、RDB における既存テーブルを対象とした **CRUD 操作**（＝`INSERT`、`SELECT`、`UPDATE`、`DELETE`）を行う SQL について学んできました。これらは、SQL のなかでも **DML**（＝**Data <u>Manipulation</u> Language**）に分類されるもので、いわば <span class="masked">データ (レコード) をどのように操作するか</span> という視点での学びでした。

ここから、次の段階として「データベース設計」、つまり、**データ (レコード) をどのようなテーブル構造で管理するか** という「考え方」について学んでいきます。具体的には <span class="masked">システムが扱う対象世界をどのようにモデル化し、それをどのようなテーブル構造として表現するか</span> について考えていきます。

なお、設計したテーブル構造を実際に定義したり、運用開始後にその構造を変更したりする際には、**DDL**（**Data <u>Definition</u> Language**：データ定義言語）に分類される SQL 文を使用します。


::: {.balloon .char-01 .face-05 .tone-blue}
RDB の特徴のひとつである **テーブルの結合** ( `JOIN` ) については、データベース設計を学んだあと (後期中間試験以降) に扱います。
:::

2年生前期の「情報2」の授業のなかでも触れたように、SQL の命令群は、その役割によって **DML (データ操作)**、**DDL (データ定義)**、**DCL (データ制御、Data <u>Control</u> Language)** に分類されます。

- **DML**：データ (レコード) の追加・検索・更新・削除 ( `INSERT`、`SELECT`、`UPDATE`、`DELETE` など) 
- **DDL**：テーブルやデータベースの構造の定義・変更・削除 ( `CREATE`、`ALTER`、`DROP` など)
- **DCL**：アクセス権限の設定・管理 ( `GRANT`、`REVOKE` など)

### データベース設計の3段階 (概念設計・論理設計・物理設計)

データベース設計は、大きく ① **概念設計** (Conceptual Design)、② **論理設計** (Logical Design)、③ **物理設計** (Physical Design) の3段階に分けられ、**抽象度の高いモデルから具体的な実装に向かって段階的に設計を進めること**が、教科書的な作法とされています。

::: {.balloon .char-01 .face-02 .tone-yellow}
ただし、実務においては、各段階を明確に区切って設計するとは限らず、複数の段階をまとめて扱ったり、前の段階に戻って設計を見直したりすることも一般的です。
:::

以降、多数の専門用語が登場しますが、**まずは細部にこだわらず、全体像を理解することを優先**してください。そのうえで、気になる用語があれば、ウェブや生成AIを利用して概要を掴んでみてください。

### 概念設計

データベース設計の最初の段階となる「**概念設計**」では、現実世界に存在する「情報」と「それらの関係」を抽出・整理し、<span class="masked">システムで何を管理する必要があるのかを明確にして、関係者間でそれらの認識を共有すること</span> を目指します。

ここで注意すべきは「**どのようなテーブルやデータ構造で実装するか**」ではなく「**何を管理し、それらがどのような関係にあるのか**」を検討・共有することになります。

- そのため、「概念設計」の段階では原則として「リレーショナルモデル」や「ドキュメント指向モデル」などの特定のデータモデルには依存しない内容を設計します。

そして、このようにデータベースによって管理する「情報」や「その関係」を抽象的に表現したものを <span class="masked">概念データモデル</span> と呼びます。代表的な表現方法には [概念ER図](https://www.google.com/search?q=概念ER図&tbm=isch) (Conceptual Entity Relationship Diagram)、[拡張ER図](https://www.google.com/search?q=拡張ER図&tbm=isch) (Enhanced/Extended ER Diagram)、[UMLクラス図](https://www.google.com/search?q=UMLクラス図&tbm=isch) (UML Class Diagram) などがあります。

::: {.balloon .char-01 .face-05 .tone-blue}
「概念設計」は、特定のデータモデルや実装方法に依存しないことを原則とします。ただし、実務 (実際の開発現場) では、この原則を踏まえつつも、利用するデータモデルを念頭に置いて設計を進めることが少なくありません。

例えば、RDBを前提とする場合は、エンティティ間の関係をER図で表現する方法が一般的となります。一方、[MongoDB](https://www.mongodb.com/ja-jp) のような「JSONドキュメントデータベース」を前提とするようなときは、エンティティ間の関係だけでなく、データの階層構造や、どの情報をひとつのドキュメントにまとめるかといった点も意識した設計が行われます。
:::

### 論理設計

「**論理設計**」とは、「概念設計」で整理した情報やその関係を、データベースモデルとして採用したものに適した具体的なデータ構造へと落とし込むプロセスです。

例えば、リレーショナルモデルを採用した場合には、管理すべき情報を「テーブル」として整理し、カラムの構成や主キー、外部キーなどを定義します。このように、データベースの論理的な構造を定義する作業は「論理スキーマの設計」とも呼ばれます。

この論理設計においては、データの冗長性を減らし、データの追加・更新・削除に伴う不整合を防ぎやすくするために <span class="masked">正規化 (Normalization)</span> という考え方が極めて重要となってきます。一般に、**第1正規形** (1NF: First Normal Form) から **第3正規形** (3NF: Third Normal Form) までを中心に検討し、必要に応じてボイス・コッド正規形なども考慮します。

- テーブルの「正規化」については、次回の講義で詳しく解説します。

リレーショナルモデルを前提とした「論理設計」のアウトプットとしては、**論理ER図** (Logical Entity Relationship Diagram) や、テーブル構造を記述した **簡略化した CREATE TABLE 文 (SQL)** などが挙げられます。

::: {.balloon .char-01 .face-02 .tone-yellow}
ここでの「**簡略化した CREATE TABLE 文**」とは、インデックスや使用する RDBMS 固有の設定などを省き、テーブル名、カラム名、データ型、主キー、外部キーなどを中心に、標準SQLに沿って記述した `CREATE` TABLE 文を指します。特定のRDBMSへの依存をできるだけ避け、論理的なテーブル構造を表現することを目的としています。
:::

:::prompts

- データベースに関する文脈で「特定の RDBMS に依存しない標準 SQL」とはどういうことですか。具体的な例を含めて解説してください。ちなみに自分は PostgreSQL で DB の勉強をしています。

:::

### 物理設計

リレーショナルモデルを前提とした「論理設計」では、テーブルやカラム、主キー、外部キーなどの論理的な構造を定義しました。これに対して「**物理設計**」では、**PostgreSQL や MySQL などの具体的な RDBMS や実行環境を前提として、データベースの実装方法や各種設定を決定します**。

例えば、検索処理を高速化するための **インデックス** ( `CREATE INDEX` ) の設計、データ型や制約の実装方法、ストレージの構成などを検討し、処理性能やデータの格納効率を高めます。また、障害に備えた冗長化やバックアップ、負荷分散、ユーザのアクセス権限やロールなどについても、運用面を考慮して設計します。

- 物理設計の内容を具体化する際には、テーブルやインデックスなどの構造を定義する **DDL** (Data Definition Language) と、ユーザやロールに対するアクセス権限を設定する **DCL** (Data Control Language) が用いられます。

::: {.balloon .char-01 .face-05 .tone-blue}
論理設計が「**どのようなデータ構造にするか**」を決めるのに対し、物理設計では「**それを具体的な環境でどのように実現し、効率的かつ安定して運用するか**」について検討・決定していきます。
:::

物理設計については、本講義では詳しく扱いません。一般的な内容については [達人に学ぶDB設計徹底指南書 第2版](https://www.amazon.co.jp/dp/B0D8N5G9GT) を、PostgreSQL については [内部構造から学ぶ PostgreSQL 設計・運用計画の鉄則 (改訂3版)](https://www.amazon.co.jp/dp/B0BLY4SPC4) などを参考にしてください。


#### 定着確認

- データベース設計において、具体的な DBMS 製品や運用環境を前提とし、データベースの実装方法や効率的かつ安定した運用方法について検討するのは「概念設計」「論理設計」「物理設計」のうち、どの段階か答えよ。
  - **答え**: <span class="masked">物理設計</span>
- RDB における「物理設計」に該当するものを<u>すべて選び</u>、番号で答えよ。
  1. よく実行される検索に合わせて、インデックスを設計する。
  2. 利用者が退会したあとも、その利用者の記事を保存するかどうかを関係者と確認する。
  3. 障害に備えて、ストレージの冗長化やバックアップの構成を決定する。
  4. 閲覧担当者と更新担当者を区別し、それぞれのアクセス権限やロールを設計する。
  5. 利用者と記事のテーブルについて、カラム構成や主キー・外部キーを定義する。
      - **答え**: <span class="masked">1、3、4。2 は概念設計、5 は論理設計に該当</span>
- RDB の物理設計に関連する SQL として、テーブルやインデックスの定義に用いる命令は ( ① )、アクセス権限の管理に用いる命令は ( ② ) に分類される。各括弧にあてはまる語を「DML」「DDL」「DCL」から選び答えよ。
  - **答え**: <span class="masked">① DDL、② DCL</span>
- 「テーブルやキーの論理的な構造が完全に同じであれば、使用する DBMS 製品やサーバの構成が異なっても、物理設計の内容は必ず同じになる」という説明は「適切である」か「適切ではない」かを答えよ。
  - **答え**: <span class="masked">適切ではない</span>

## データベースの概念設計 (詳細)

データベースの「**概念設計** (Conceptual Design)」では、システムが対象とする世界について **どのような情報を管理し、それらがどのような関係にあるのか** を明らかにして整理していきます。

具体的には、関係者へのヒアリングや資料分析などを通じて **業務要件** や **ビジネスルール** を確認し、対象世界 (現実世界) の情報構造を抽象化した「**概念データモデル**」を作成し、それを可視化表現した「**概念ER図**」などを作成します。

- 概念設計の段階では、テーブルやカラムなどの具体的な実装方法ではなく、管理すべき情報の全体像を整理することがポイントとなります。

::: {.note .type-senior}
**中級者向け: ビジネスルールの発見も設計の仕事**

現場では当たり前とされているルールほど、明文化されていないことがあります。そのため、ヒアリングでは <span class="masked">「例外はありませんか？」や「こういう場合はどうなりますか？」</span> など、具体的な状況を想定して掘り下げて確認することが求められます。

- 特に <span class="masked">「通常は〜」「基本的には〜」</span> という回答があったときには注意する必要があります。このような表現が出てきたときには、聞き流さずに「**例外となるケース**」についてしっかりと確認・記録するようにしてください。

**すべてのビジネスルールを「データベースの制約」として実現できるわけではありません**。「データベース側」ではなく「アプリ側で制御すべき制約」もあるため、個々のビジネスルールについて、どこで、どのように実現するかを検討することも必要となります。
:::

### 概念ER図とは

**概念ER図** (Conceptual Entity Relationship Diagram) とは、対象世界 (現実世界) の情報構造を **_エンティティ_** (**Entity**、実体) と、**_リレーションシップ_** (**Relationship**、関連) という2つの基本要素によって表現した図となります。

例えば、PG3 で開発したような「**ブログシステム**」を対象としたとき、設計の一例として、次のような「概念ER図」を作成することができます。

![img](figs/06/CER-01-1.png)

この図において、**User** や **Article** などの四角形が「**エンティティ**」、それらを結ぶ青色の線が「**リレーションシップ**」を表しています。つまり、

- 何を管理するのか 👉 <u>エンティティ</u> (実体)
- それらがどのような関係にあるのか 👉 <u>リレーションシップ</u> (関係・関連)

として、視覚的に整理・構造化されています。

なお、ER図には **IE記法** (アイイー記法) や **IDEF1X記法** (アイデフワンエックス記法)、**Chen記法** (チェン記法) など、様々な表現方法が存在しており、それぞれでエンティティやリレーションシップの表現に使用する記号や規則が異なっています。実際に `概念ER図` で画像検索すると、様々な記法 (亜種や独自のカスタマイズを含む) があることが確認できると思います。

- [「概念ER図」で画像検索した結果](https://www.google.com/search?q=概念ER図&tbm=isch) @ Google検索 (画像)
- [「Conceptual Entity Relationship Diagram」で画像検索した結果](https://www.google.com/search?q=Conceptual+Entity+Relationship+Diagram&tbm=isch) @ Google検索 (画像)

::: {.balloon .char-01 .face-02 .tone-yellow}
実務では、**IE記法** (特に **Crow's Foot記法**) が広く利用されているため、本講義でも **IE記法のみ** を扱います。なお、ER図にはさまざまな記法があるものの、**エンティティやリレーションシップ、多重度といった基本的な考え方は共通**しています。
:::

::: {.balloon .char-01 .face-04 .tone-blue}
IPAの「**データベーススペシャリスト試験**」などでは、ER図に相当する概念データモデルが出題されます。ただし、[2025年度の過去問](https://www.ipa.go.jp/shiken/mondai-kaiotu/nl10bi0000009lh8-att/2025r07a_db_pm1_qs.pdf#page=3) のように、**IE記法とは異なる表記ルール** が使用されることもあります。

資格試験の学習では、**問題冊子に示された表記ルールを確認し、本講義で学んだ知識と対応づけて理解すること** が重要となります。

### 「エンティティ」とは

RDB において「**テーブル**」に相当するものが <span class="masked">エンティティ (Entity)</span> となります。日本語では「実体」と訳されますが、**必ずしも物理的な存在を意味するわけではなく**、**イベント (出来事)** や **抽象的な概念** も「エンティティ」としてモデル化されます。

概念ER図において、エンティティは一般に「四角形」で表現されます。

::: {.balloon .char-01 .face-02 .tone-yellow}
例えば、ブログであれば、Article (記事)、Comment (コメント)、Category (カテゴリ)、User (ユーザ) といったものが「エンティティ」としてモデル化されます。概念設計の段階では細部までは詰めませんが、エンティティは、一般に複数の **アトリビュート** (**属性**) を持ちます。

「**アトリビュート** (**属性**) 」とは、RDB で <span class="masked">カラム</span> に相当するものです。例えば、**Article** エンティティは、**title**、**body**、**created_at** といったアトリビュートを持つと考えられます。
:::

- オブジェクト指向の考え方で言えば、オブジェクトが <span class="masked">エンティティ</span>、プロパティが <span class="masked">アトリビュート</span> に相当します。

#### 定着確認

- 次に示すものは、ある学校の図書館における貸出管理システムの概要を説明したものである。この説明から、データベースで管理すべきエンティティを抽出せよ。
  - **答え**: <span class="masked">学生、本、貸出、著者。※ あくまで一例であり、ほかにも妥当な設計が考えられます。</span>  
  
> ある学校の図書館では、学生が本を借りることができます。図書館にはさまざまな本が登録されており、学生が本を借りた際には、誰がどの本を借りたのか、いつ借りたのか、いつ返却したのかを記録しています。また、本の著者についても情報を管理しています。

- 次に示すものは、ある学校の課題管理システムの概要を説明したものである。この説明から、データベースで管理すべきエンティティを抽出せよ。
  - **答え**: <span class="masked">学生、教員、授業、課題、提出物。※ あくまで一例であり、ほかにも妥当な設計が考えられます。</span>  
  
> ある学校では、教員が授業ごとに課題を出し、学生は指定された期限までに課題を提出します。システムでは、授業の情報や課題の内容、提出期限を管理するとともに、学生が提出したファイルや提出日時、教員による評価結果なども記録しています。

#### エンティティとして扱うべきか、アトリビュートとして扱うべきかの判断

ある情報を「エンティティ」として扱うか、「アトリビュート」として扱うかは、**設計目的やビジネスルール、運用上の要件によって変わるものであり、あらゆるシステムに共通する絶対的な正解があるわけではありません**。とはいえ、この判断を誤ると、ビジネスロジックやデータ処理の実装が複雑になり、将来的に大きな **技術的負債** となる可能性があります。特に、運用開始後にデータ構造を変更する場合、既存データの移行やアプリケーションの修正など、多大なコストが発生することもあります。

::: {.balloon .char-01 .face-01 .tone-pink}
データベース設計について、AIの提案を十分に検証せずに採用すると、設計全体に長期的な悪影響を及ぼす技術的負債が生まれる可能性があります。
:::

エンティティとアトリビュートの区別は、システム全体の設計意図を踏まえ「**何を、どのような目的で管理する必要があるのか**」を考えて判断することが重要となります。

---

例えば、ゲームのキャラクタが持つ「**ジョブ**」という情報について考えてみます。キャラクタごとに `Priest` や `Monk` といった **ジョブ名を記録するだけ** であれば、**Character** というエンティティ (テーブル) に **job** というアトリビュート (カラム) を設け、文字列として保持する方法が考えられます。

![img](figs/06/job.png)

一方、**ジョブごとの特性として、攻撃補正、防御補正、魔法補正、フレーバーテキストなども管理する** のであれば、**Job** という独立したエンティティ (テーブル) を設け、ジョブ名や各補正値をアトリビュート (カラム) として管理する設計が考えられます。

この場合、**Character** と **Job** を関連づけることで、同じジョブに属するキャラクタが共通のジョブ情報を参照できるようになります。例えば、`Priest` の防御補正を変更する場合も、Job 側の情報を更新するだけで済み、各キャラクタのデータを個別に書き換える必要がなくなります。

::: {.balloon .char-01 .face-05 .tone-blue}

例えば「**住所**」は単なる文字列の「**アトリビュート**」として管理できます。一方、<u>1 人の利用者が複数の住所を登録でき、それぞれについて登録日や用途 (自宅・配送先など) を管理する必要があれば</u>、住所を独立した「**エンティティ**」として扱う設計が考えられます。

また「**所持金**」はキャラクタの「**アトリビュート**」として管理できますが、<u>入出金の履歴まで記録したいのであれば</u>、取引履歴という別の「**エンティティ**」を追加する設計が考えられます。

このように、管理する情報の範囲が広がることで、新たなエンティティが必要になる場合もあります。
:::

なお、エンティティは、細かく分割すればよいというわけではありません。過度な分割は、<span class="masked">以降の論理設計や実装</span> を複雑にする可能性があります。そのため、データの整合性や保守性、実装時の性能なども見据えながら、適切な粒度でエンティティを設計することが重要です。

:::{.note .type-senior}
**概念設計でアトリビュート (属性) を表現したい場合は？**

工程を形式的に分ける説明では「概念設計でエンティティと関係を整理し、論理設計でアトリビュート (属性) を詳しく検討する」と区分し、概念ER図にはアトリビュート (属性) を記載しない流儀もあります。ただし、これはすべての資料や設計現場に共通する絶対的な規則ではありません。

実際には、概念設計の段階からアトリビュート (属性) を検討しても問題ありません。例えば、先ほどの **Job** のように「ジョブ名だけでなく、攻撃補正や防御補正なども管理したい」と考えることで、**独立したエンティティとして扱う必要性に気づくこともあります**。このように、設計工程を柔軟に行き来しながら、管理すべき情報やその関係を整理していくことも重要となります。

概念ER図のなかにアトリビュートを記載する場合には、例えば `Character (name, level, job)` のように表現する方法があります。

![img](figs/06/CER-01-8.png)

### リレーションとは (多重度のみの表現)

ER図における **リレーション** とは「**エンティティ同士の関係 (関連や結びつき) を表現するもの**」となります。例えば「ブログシステム」において...

- 1つの Article (記事) には **複数の Comment (コメント) を付けることができる**。
- 1つの Comment (コメント) は **必ず1つの Article (記事) に属する**。

...のようなエンティティ間の関係があるとき、ER図では次のように、**線と Crow's Foot** (カラス足<i class="fa-solid fa-crow"></i> ) などの端点記号を使ってリレーションを表現します。

![img](figs/06/CER-01-3.png)


ここで、リレーションの両端に付けられた記号は、**一方のエンティティ1件に対して、もう一方のエンティティが何件対応するか**を表しています。このようなエンティティ同士の <span class="masked">数量的な関係や制約</span> を **カーディナリティ (多重度)** と呼びます。そして、ER図では、この **カーディナリティ (多重度)** を Crow's Foot などの記号で表現します。

例えば、下図の <font color="deeppink">❶</font> のような **カラス足の記号** ( `多` を表す記号) は、「1つの Article に、**複数の Comment を付けることができる**」という数量的な関係を表しています。

![img](figs/06/CER-01-4.png)

一方、<font color="deeppink">❷</font> のような **縦棒の記号** (数字の `1` を表す記号) は、「1つの Comment は、**1件の Article に属する**」という数量的な関係を表しています。

このようなエンティティ同士の関係は、「Article と Comment は `1対多` (`1:多`、`1:N`) の関係にある」のように表現します。

リレーションをER図で表現するときは、**一方のエンティティを1件とした場合に、相手が何件対応するか**を考えます。これを両方向について確認し、それぞれの端点に対応するカーディナリティ (多重度) の記号を付けます。

1. **1件の Article に、Comment は最大何件あるか。**
    - 複数件のコメントを付けられるので、**Comment 側の端点**にカラス足の記号を付けます。
2. **1件の Comment は、何件の Article に属するか。**
    - 1件の記事に属するので、**Article 側の端点**に縦棒の記号を付けます。

::: {.balloon .char-01 .face-02 .tone-yellow}
リレーションを読み取るときは、一方のエンティティを1件に固定し、相手が何件対応するかを考え、**相手側の端点に付けられた記号から読み取ります**。

例えば「Article を1件に固定したら、Comment は何件対応するか」と考え、その答えを <span class="masked">Comment</span> 側の端点に付けられた記号から確認します。

なお、ここでは `1` と `多` の区別だけを扱っています。「0件でもよいか」「必ず1件以上の関係が必要か」といった条件については、このあとの [リレーションとは (多重度と任意性の表現)](#リレーションとは-多重度と任意性の表現) で説明します。
:::

---

別の例で考えてみます。例えば、ER図で **Student** (学生) と **Subject** (科目) という 2 つのエンティティの関係が、次のように表現されているとします (リレーションの **両端** が `多` となっている)。

![img](figs/06/CER-01-5.png)

このER図は、次のような関係を表しています。

- 1人の Student は、**複数の Subject を受講できる** (A Student **takes** multiple Subjects.)。
- 1つの Subject は、**複数の Student に受講される** (A Subject is taken by multiple Students.)。

このような関係を **多対多 ( `N:M` )** の関係と表現します。

:::{.note .type-tips}
**ER図の関連名 (Relationship Name) について**

IE記法のER図では、エンティティ同士の関係をより分かりやすくするために、リレーションを表す線上に **関連名 (Relationship Name)** を付けることがあります。

例えば、下図では Article と Comment の関係を `has` という英語の **動詞句 (Verb Phrase)** で補足しています。これは「Article は Comment を**持つ**」という関係を言葉で説明したものです。

![img](figs/06/CER-01-3.png)

このように、関連名は**エンティティ同士の関係を自然言語で説明するための補助的な表現**となります。そのため、<span class="masked">関係が明らかな場合には省略</span> されることもあります。

なお、関連名は以下のように「**どちらのエンティティを主語にするか**」によって変わります。

- **Article を主語にする場合**：Article `has` Comment (記事はコメントを持つ)。
- **Comment を主語にする場合**：Comment `belongs to` Article (コメントは記事に属する)。

この例では、Article を基準にすると `has` ですが、Comment を基準にすると `belongs to` という表現になります。

![img](figs/06/CER-01-7.png)

どちらのエンティティを基準 (主語) にするかについて厳密な決まりは無く、一般には「より中心的なエンティティ」や「動作・行為を起こす側」を基準にすることが多いです。

ER図でよく使用される関連名 (動詞句) には、次のようなものがあります。

- has / belongs to
- contains / is contained in
- creates / is created by
- manages / is managed by
- owns / is owned by
- includes / is included in
- references / is referenced by

:::

### リレーションとは (多重度と任意性の表現)

前のセクションでは、**カーディナリティ (多重度)** のみに着目してリレーションを表現しました。

しかし、実際のER図では、多重度に加えて、**対応するエンティティが必ず存在するのか、それとも存在しない場合もあるのか**を示す **オプショナリティ (任意性)** についても表現することが推奨されます。

オプショナリティは、**必須** (少なくとも1件の対応が必要) を数字の `1` に似た縦棒で表し、**任意** (0件でもよい) を数字の `0` に似た丸印で表します。

![img](figs/06/CER-02-1.png)

上図の Comment 側の端点では、`多` を表すカーディナリティの記号と、`0` (任意) を表すオプショナリティの記号が組み合わされています。これは、「1件の Article に対して、**0件以上の Comment が対応することができる** (＝<span class="masked">Comment が1件も付いていない Article も存在し得る</span>)」ことを表しています。

一方、Article 側の端点では、`1` を表すカーディナリティの記号と、`1` (必須) を表すオプショナリティの記号が組み合わされています。これは、「1件の Comment は、**必ず1件の Article に属する** (＝<span class="masked">どの Article にも属さない Comment は存在し得ない</span>)」ことを表しています。

::: {.balloon .char-01 .face-05 .tone-blue}
別の見方をすると、オプショナリティはエンティティ間の対応件数の **下限** ( `0` または `1` ) を、カーディナリティは **上限** ( `1` または `多` ) を表しているとも言えます。

例えば、データベース設計では `1..*` や `0..1` のように件数の範囲を表現することがありますが、このとき下限が **オプショナリティ**、上限が **カーディナリティ** に対応します。
:::

ここで、前のセクションで説明した両方向の考え方に、最小件数も加えてみましょう。

- **1件の Article に対する Comment** は、最小0件、最大は複数件 (上限なし) です。この2つの条件を、**Comment 側の端点**に記号で表します。
- **1件の Comment に対する Article** は、最小1件、最大1件です。この2つの条件を、**Article 側の端点**に記号で表します。

それぞれの端点では、**エンティティの四角形に近い記号が最大件数、その内側 (線の中央寄り) の記号が最小件数**を表します。例えば、上図の Comment 側では、四角形に近いカラス足が「多」、その内側の丸印が「0」を表しています。

::: {.balloon .char-01 .face-02 .tone-yellow}
任意性を検討するときは、まず片側を1件に固定し、相手が「最少何件、最大何件」かを考えます。その答えを相手側の端点に置いてから、逆方向も同じように考えると整理しやすくなります。
:::

カーディナリティとオプショナリティを組み合わせると、Crow's Foot 記法では、次の **4パターン** の端点記号を使用することになります。

![img](figs/06/CER-02-2.png)

以降、試験や小テストを含め、特に指示がない限り、ER図では **カーディナリティとオプショナリティの両方を考慮した表現**を使用してください。

::: {.note .type-tips}
**リレーションの具体的な上限数は考慮せずともよいのか？**

ここまでに学んだIE記法の基本記号では、最大件数を `1` または `多` で表現します (`多` は `*` や `N` と表記することもあります)。

例えば、「1人のキャラクタは最大3つのギルドに所属できる」という条件があっても、Guild 側の最大件数は `多` と表現します。最小件数については、未所属を認めるかどうかに応じて `0` または `1` を指定します。

しかし、**ER図の基本記号で区別できないことと、設計上考慮しなくてよいことは別です**。「最大3件」という条件もシステムが満たすべき重要な要件であり、ER図の注記や要件定義書などに記録しておく必要があります。その条件を実際にどのように守るかは、後続のデータベース設計やアプリケーション設計で具体化します。
:::

### 概念ER図を作成することの意義

概念ER図 (概念データモデル) を作成・共有することで、<span class="masked">自然言語による説明では曖昧になりやすいエンティティ同士の関係</span> を、**明示的かつ一貫した形式で表現・共有することができます**。図として可視化することで、データモデルの構造や全体像を理解しやすくなり、チーム開発におけるメンバー間の認識の齟齬や、それに起因する手戻りを防ぐことにもつながります。

また、適切なツールを利用すれば、自然言語で詳細な説明を記述するよりも、効率的にER図を作成することができます。例えば、次の概念ER図が表している内容を文章で説明しようとすると...

![img](figs/06/CER-01-1.png)

...次のようになります。エンティティやリレーションの数が増えるほど、自然言語での説明は長くなり、内容も複雑になっていくことが分かると思います。

> - 1人の User は、0件以上の Article を作成できる (Article を1件も作成していなくてもよい)。
> - 1件の Article は、必ず1人の User によって作成される。
> - 1件の Article には、0件以上の Comment を付けることができる (Comment が1件も付いていなくてもよい)。
> - 1件の Comment は、必ず1件の Article に属する。
> - 1件の Comment は、必ず1人の User によって作成される。
> - 1人の User は、0件以上の Comment を作成できる (Comment を1件も作成していなくてもよい)。
> - 1件の Article は、必ず1つ以上の Category に属する (どの Category にも属さないことは認められない)。
> - 1つの Category には、0件以上の Article が属することができる (Article が1件も属していなくてもよい)。

このように、誤解や認識の齟齬を避けようとして条件を丁寧に記述すると、**どうしても説明が冗長になりがち**で、その作成や修正、確認にも手間がかかります。さらに、文章を列挙するだけでは <span class="masked">リレーションの記述漏れ</span> が生じやすく、**エンティティ同士の関係やデータモデルの全体像を把握することも難しくなります**。

こうした理由から、データベース設計では、エンティティ同士の関係を視覚的に整理・共有するためにER図が広く活用されています。

::: {.balloon .char-01 .face-05 .tone-blue}
ER図は設計者だけが利用するものではなく、**開発に携わるメンバーが共通認識を持つための重要な資料**でもあります。そのため、ジュニアレベルのエンジニアであっても「ER図を正しく読み解く力」が求められます。

次のセクションで扱う「論理ER図」も含めて、しっかりと理解するようにしてください。
:::

### 概念設計からモデル選定へ

概念設計が完了したら、次は **データベースモデルの選定** を行います。ここでは、作成した概念ER図 (概念データモデル) やシステム要件を踏まえ、**代表的なユースケースを具体的に想定しながら**、どのデータベースモデルが適しているかを検討します。

モデルの選定では、主に次のような観点が重要になります。

- **検索・更新処理の特徴**：複雑な検索や集計が必要なのか、キーを指定した単純な読み書きが中心なのか。また、更新時にどの程度のデータ整合性が求められるのか。
- **データ構造の特徴**：データ同士の関係が複雑なのか、データ構造 (スキーマ) が頻繁に変化するのか。また、その変更にどの程度柔軟に対応する必要があるのか。
- **アクセスの頻度や性能要件**：読み取りと書き込みのどちらが中心なのか。また、どの程度の応答速度やスループット (＝一定時間あたりに処理できるデータ量やリクエスト数) が求められるのか。

どのデータベースモデルが適しているかは、システムに求められる要件によって異なります。代表的なモデルと、それぞれが適しているケースを次に示します。

- **リレーショナルデータベース (RDB)**：複数のデータを関連付けた検索・集計や、トランザクションによる整合性の確保を重視する場合。
    - 代表的なDBMS：[PostgreSQL](https://www.postgresql.org/)、[SQLite](https://www.sqlite.org/)、[MySQL](https://www.mysql.com/)、[Microsoft SQL Server](https://www.microsoft.com/ja-jp/sql-server) など
    - 代表的なクラウドサービス：[Supabase](https://supabase.com/)、[Neon](https://neon.com/)、[Amazon RDS](https://aws.amazon.com/rds/)、[Amazon Aurora](https://aws.amazon.com/rds/aurora/)、[Azure SQL Database](https://azure.microsoft.com/ja-jp/products/azure-sql/database) など
- **ドキュメント指向データベース (DocDB)**：柔軟なデータ構造が必要で、ドキュメント単位でのデータ取得・更新が中心となる場合。

    - 代表的なクラウドサービス：[Upstash Redis](https://upstash.com/)、[Redis Cloud](https://redis.io/cloud/)、[Amazon DynamoDB](https://aws.amazon.com/dynamodb/) (ドキュメントモデルにも対応)、[Cloudflare Workers KV](https://developers.cloudflare.com/kv/)、[Amazon ElastiCache](https://aws.amazon.com/elasticache/) (エラスティキャッシュ) など

## 論理設計

論理設計では、概念ER図を **リレーショナルデータベース (RDB) の構造に合わせて整理**し、次のような **_論理ER図_** (Logical Entity Relationship Diagram) を作成していきます。

![img](figs/06/LER-01-1.png)

具体的には、概念ER図を 次のような方針 (＝<span class="masked">RDBでデータを効果的・効率的に管理するための考え方</span> ) に沿って整理し、テーブルやカラム、キーといった RDBでの実装を意識した構造に近づけていきます。

1. 各エンティティに必要なアトリビュート (属性) を整理し、テーブルとカラムを定義する。
2. 階層構造や <span class="masked">列方向の繰り返し構造</span> を避け、データを2次元の表 (テーブル) として整理する。
3. 各セルに格納するデータは、原則として <span class="masked">単一の値 (スカラー値)</span> とし、集合や配列などを含まない構造にする。
4. 各テーブルのレコード (行) を一意に識別する **主キー** (**Primary Key**) を設定する。
5. `多対多` のリレーションは、**中間テーブル** (関連エンティティ) を導入して、`1対多` の関係に分解する。
6. データの重複や更新時の不整合を防ぐため、必要に応じて **正規化** (1NF → 2NF → 3NF) を行う。

なお、論理設計では RDB でのデータ管理を意識しますが、PostgreSQL や SQLite などの <span class="masked">個別製品に固有の仕様や制約</span> については、原則として扱いません。これらは、論理設計に続く物理設計で具体的に検討します。

#### 定着確認

- データベースの論理設計において、エンティティは RDB における (　①　) に相当する。また、アトリビュート (属性) は、RDB における (　②　) に相当する。各括弧にあてはまるもっとも適切な語をカタカナで答えよ。
  - **答え** : <span class="masked">①テーブル。②カラム</span>

- テーブルの各セルに格納する、集合や配列ではない単一の値を (　　　) という。括弧にあてはまる語を答えよ。
  - **答え**: <span class="masked">スカラー値 (スカラ値)</span>

- テーブルのレコード (行) を一意に識別するために設定するキーを、日本語と英語で答えよ。
  - **答え**: <span class="masked">主キー。Primary Key</span>

- RDBの論理設計では、「多対多」のリレーションを、そのまま 2 つのテーブル間に定義するのではなく、(　　　) を導入して「1対多」の関係に分解する。括弧にあてはまる語を答えよ。
  - **答え**: <span class="masked">中間テーブル または 関連エンティティ</span>

- データの重複や更新時の不整合を防ぐため、1NF、2NF、3NFなどの段階に沿ってテーブルの構造を整理することを何というか答えよ。
  - **答え**: <span class="masked">正規化</span>

#### テーブルとカラムの洗い出し

論理設計では、まず「概念ER図」に表現されたエンティティを「テーブル」として捉え、それぞれの **カラム構成を検討**していきます。

::: {.balloon .char-01 .face-05 .tone-blue}
本講義では一般的な RDB の命名慣習に合わせ、**テーブル名**は <span class="masked">可算名詞の複数形 (集合名詞はそのまま) のスネークケース</span>、**カラム名**は「単数形のスネークケース」で統一します。
:::

各カラムのデータ型については、文字列型、数値型、日時型といった **大まかな分類で検討**しておきます ( `VARCHAR(16)`、`INTEGER`、`TIMESTAMP` など、具体的なデータ型の決定は「物理設計」において行います)。

以下は、「概念ER図」からテーブルとカラムを洗い出して整理した例です (整理方法に決まった書式があるわけではありません)。

```
- `users` テーブル (User エンティティ)
  - `name`       文字列型
  - `email`      文字列型
  - `created_at` 日時型
  - `updated_at` 日時型

- `articles` テーブル (Article エンティティ)
  - `title`      文字列型
  - `content`    文字列型
  - `created_at` 日時型
  - `updated_at` 日時型

(以下、略)
```

ここで、各テーブルのカラムは、基本的に **スカラー値**、つまり <span class="masked">配列やオブジェクトのような内部構造を持たない単一の値</span> を格納するように設計します。

例えば、**position** というカラムに `[10, 20]` のような **配列** を格納したり、**class** というカラムに `{"grade": 4, "course": "I"}` のような **辞書 (オブジェクト)** を格納したりするのではなく、次のように個々の値を独立したカラムとして定義します。

- **position** は、`pos_x` と `pos_y` に分け、それぞれにスカラー値 (数値) を格納する。
- **class** は、`grade` と `course` に分け、それぞれにスカラー値 (数値、文字列) を格納する。

このように、1つのカラムに複数の情報をまとめて格納することを避け、**各カラムが単一の値を持つ構造**に整理することが、次回講義で扱う **第1正規形 (1NF)** の基本的な考え方となります。

:::prompts

### 繰り返しカラムは別テーブルで管理

テーブル内に **同種の情報を繰り返し格納するカラム構成** がある場合は、その部分を別テーブルに分離し、リレーションによって関連付けることを検討します。

例えば、**characters** テーブルに、次のような **skill_1**、**skill_2**、**skill_3**、**skill_4** といったカラムを持たせる設計は、**RDB における典型的なアンチパターン** の1つです。

| name | job | skill_1 | skill_2 | skill_3 | skill_4 |
|:--:|:--:|:--:|:--:|:--:|:--:|
| Alice | Priest | Heal | Resurrection | <font color="lightgray">NULL</font> | <font color="lightgray">NULL</font> |
| Bob | Monk | DragonKick | <font color="lightgray">NULL</font> | <font color="lightgray">NULL</font> | <font color="lightgray">NULL</font> |

- 🚨 **アンチパターン** とは、一般に問題が生じやすいと知られている設計や実装の典型例を指します。

このような構造では、習得できるスキルの上限数が増えるたびにカラムを追加する必要があるほか、スキルの検索や集計が複雑になるといった問題があります。

::: {.balloon .char-01 .face-04 .tone-pink}
例えば「Heal を持つキャラクタ」を検索する場合、次のように `WHERE` 句で複数のカラムを指定する必要があり、SQLが煩雑になります。

```sql{.numberLines caption="Healを持つキャラを検索するためのWHERE句"}
SELECT name
FROM characters
WHERE skill_1 = 'Heal'
  OR skill_2 = 'Heal'
  OR skill_3 = 'Heal'
  OR skill_4 = 'Heal'
```
:::

そこで、繰り返し出現する情報を別テーブル (ここでは **skills** テーブル) に分離し、**同種の情報を行として縦方向に保持する構造** (＝「縦持ち」「行持ち」「long format」) に変更します。

**▼ 分離後の characters テーブル**

| name | job |
|:--:|:--:|
| Alice | Priest |
| Bob | Monk |

**▼ 分離後の skills テーブル**

| character_name | skill | slot_no |
|:--:|:--:|:--:|
| Alice | Heal | 1 |
| Alice | Resurrection | 2 |
| Bob | DragonKick | 1 |

このようにテーブルを分離すると、「概念ER図」は次のようになります。

![img](figs/06/CER-02-4.png)

ここでは、キャラクタとスキルの対応関係を名前によって示し、**繰り返しカラムを別テーブルの行として管理すること** に着目しています。なお、同じ名前のキャラクタをどのように区別するか、各レコードをどのように識別・関連付けるかについては、以下の「**主キー**」「**複合主キー**」「**外部キー**」のセクションのなかで解決していきます。これらのキーを設定した「論理ER図」についても、外部キーの説明後に改めて示します。

また、こうしたテーブル構造の整理は、次回講義で詳しく扱う **正規化** とも大きく関係してきます。

### 主キー (Primary Key)

テーブルを構成するカラムを整理したら、次に各テーブルの「**主キー (PK: Primary Key)**」を決めていきます。

「主キー」とは、テーブル内の各レコード (行) を <u>一意に識別できるカラム (またはカラムの組み合わせ) に設定するもの</u> です。また、「主キー」はレコードを識別するだけでなく、他のテーブルから参照する際にも使われ、その値が **外部キー (FK: Foreign Key)** として利用されることがあります。

- 「**一意に識別できる**」とは、<span class="masked">複数のレコード (行) のなかから、特定の 1 行を重複なく識別できる</span> という意味です。
- RDB では、原則として各テーブルに「主キー」を設定します。
    - ログの記録やイベントの収集など、用途によっては主キーを設けない場合もあります。
    - PostgreSQL では主キーのないテーブルも作成できますが、本講義の論理設計では、原則として各テーブルに主キーを定義します。

例えば、次のようなテーブルがあるとします。`name`、`nickname`、`age` のうち、**どのカラムを主キーとして設定できるか**を考えていきます。

|name|nickname|age|
|:--:|:--:|:--:|
|Alice|Ali|20|
|Bob|Bobby|25|
|Carol|<font color="lightgray">NULL</font>|20|
|David|Dave|23|

#### ageカラムを主キーにできるか?

**age** カラムには、同じ値 (`20`) を持つレコードが複数存在するため、各レコードを一意に識別できません。また、今後も同じ年齢のレコードが追加される可能性があるため、**age は主キーとして適していません**。

#### nicknameカラムを主キーにできるか?

**nickname** カラムには重複する値がないため、現在のデータだけを見れば、レコードを一意に識別できそうです。しかし、Carol の nickname には `NULL` が設定されています。主キーには <span class="masked">`NULL` を含むことができないという制約</span> があるため、**現在の nickname カラムをそのまま主キーにすることはできません**。

#### nameカラムを主キーにできるか?

**name** カラムには `NULL` や重複する値がなく、現在のデータだけを見れば、各レコードを一意に識別できるため、理論上は **name** を主キーにすることができます。

ただし、これはあくまで **現在のサンプルデータに重複がない** という状況における判断にすぎません。主キーを決める際には、**今後データが増えても、一意に識別できるか** まで考える必要があります。

例えば、**name** を主キーに設定すると、主キーには一意性が保証されるため (＝RDBMSにより、自動で「UNIQUE制約」が付与されるため)、<span class="masked">同じ名前を持つ別人を登録できなくなるという運用上の制約</span> が生じます。実際には同姓同名の人物が存在することは十分にあるため、**name を主キーにすることは適切ではありません**。

::: {.balloon .char-01 .face-02 .tone-yellow}
- **UNIQUE制約** とは、**一意性制約** とも呼ばれ、指定したカラム（またはカラムの組み合わせ）において重複する値の登録を制限するための制約です。
- 主キーに設定されたカラムには、**UNIQUE制約**に加えて、**NOT NULL制約** (非NULL制約) も自動的に適用されます。 
:::

このような問題を避けるため、**id** や **character_id** のような「**識別用のカラム**」を追加し、連番や UUID などを割り当てて主キーとする方法が広く用いられています。このような、データを識別するために人工的に設けるキーを「**サロゲートキー** (代理キー、Surrogate Key) 」と呼びます。

サロゲートキー (整数の連番) を追加した例を以下に示します。

| <u>id</u> | name | nickname | age |
|:--:|:--:|:--:|:--:|
| 1 | Alice | Ali | 20 |
| 2 | Bob | Bobby | 25 |
| 3 | Carol | <font color="lightgray">NULL</font> | 20 |
| 4 | David | Dave | 23 |

一方、「学籍番号」のように、<u>現実世界で意味を持ち、レコードを一意に識別するために利用できるキー</u> を **ナチュラルキー** (自然キー、Natural Key) と呼びます。メールアドレスなども、一意性が保証される設計であれば「ナチュラルキー」の候補となります。

::: {.note .type-senior}
**サロゲートキーには「連番」と「UUID」のどちらを使うべきか**

サロゲートキーには、整数の連番や、UUID、Nano ID などの識別子が利用されます。

- **連番ID** は、データサイズが小さく、検索・結合やインデックスの管理において性能面で有利です。一方、**ID が予測されやすく**、分散環境では <span class="masked">一意性を保証するための仕組みが必要</span> になります。
- **UUID v4 や Nano ID などのランダムID** は、<span class="masked">分散環境でも独立して生成しやすく、衝突する確率が極めて低い</span> という特徴があります。また、**IDの推測や列挙が困難**になる一方、連番 ID よりデータサイズが大きく、インデックスの効率で不利になる場合があります。

なお、UUID には、ランダム性と時系列順の並びやすさを組み合わせた **UUID v7** などもあり、連番IDとランダム ID の欠点を補う選択肢として利用されています。
:::

:::prompts
- RDB のサロゲートキーとして、連番ID、UUID v4、UUID v7、Nano ID を比較してください。特に、分散環境での生成、インデックス効率、セキュリティの観点から解説してください。
- ウェブアプリのバックエンドとして使用する RDB において整数値の連番 ID をサロゲートキーとして使用するときのリスクについて解説してください。
:::

### 複合主キー

テーブルの主キーは、1つのカラムだけでなく、**複数のカラムを組み合わせて設定**することもできます。このような主キーを、特に **複合主キー** (Composite Primary Key) といいます。複合主キーは、`多対多` のリレーションを `1対多` に変換するために設ける **中間テーブル** (詳細は後述) などで頻繁に使われます。

::: {.balloon .char-01 .face-05 .tone-blue}
複合主キーは、主キーであることが文脈から明らかな場合、単に「**複合キー**」と呼ばれることもあります。
:::

たとえば、キャラクタが所持しているアイテムの数量を管理するケースを考えます。

まず、**items** テーブルでは「回復薬」「剣」「盾」などの **アイテムの種類** を管理するものとします。同じ種類の回復薬が 10 個あっても、10 行のデータを登録するのではなく、「回復薬」という種類を 1 行で表すものとします。

そのうえで **character_items** というテーブルで、**どのキャラクタが、どの種類のアイテムを、何個所持しているか** を管理するものとします。ここでは個々のアイテムや過去の所持履歴は扱わず、現在の所持数だけを記録します。

ただ、この **character_items** テーブルでは、`item_id` だけでは所持しているキャラクタを区別できず、`character_id` だけではアイテムの種類を区別できないという問題があります。しかし、**`character_id` と `item_id` を組み合わせれば、各行を一意に識別可能です**。

そこで、この 2 つのカラムを複合主キーに設定します。

|<u>character_id</u>|<u>item_id</u>|quantity|
|:--:|:--:|:--:|
|1|38|3|
|1|46|1|
|2|10|5|
|2|11|2|
|2|46|1|


複合主キーには、カラムの組み合わせが重複しないことを保証する役割があります。そのため、**同じキャラクタと同じアイテムの種類について、現在の所持数量を複数行に重複登録すること**を防ぐことができます。例えば、`(character_id,item_id,quantity)=(1,38,3)` と `(1,38,4)` は同じ組み合わせなので、両方を登録することはできません。所持数が 3 個から 4 個に変わった場合は、新しい行を追加するのではなく、既存の行の **quantity** を更新します。

なお、複合主キーを構成するカラムには、一意性を保証する仕組みに加えて、NOT NULL制約 が自動的に適用されます。

::: {.note .type-senior}
**中級者向け： 複合主キー vs. サロゲートキー**

中間テーブルの主キー設計、つまり「**複合主キーとすべきか**」あるいは「**サロゲートキーを導入すべきか**」は、設計者によって意見が分かれるテーマとなっています。どちらにも一貫した理論的正当性があり、現在のところ明確な定石はありません。興味があれば、`複合主キー アンチパターン` などのキーワードで検索したり、生成AIで深掘りしてみてください。
:::

:::prompts

### 外部キーを使用した「1対多」のリレーションの表現

「概念ER図」における `1対多` のリレーションは、「論理ER図」では、`1` 側のテーブルの **主キー (PK)** を参照する「**外部キー** (FK: Foreign Key)」を、`多` 側のテーブルに設けることで表現します。

例えば、ブログシステムの「概念ER図」では、以下のように「**User** エンティティ」と「**Comment** エンティティ」が `1対多` の関係になっています。これは、<span class="masked">1 人のユーザーが 0 個以上のコメントを作成できる</span> という関係を表しています。

![img](figs/06/LER-01-6.png)

この関係を「論理ER図」で表す場合は、以下の図のように、**comments** テーブルに **users** テーブルの **主キー** (`user_id`) を参照するカラムを追加します。このようなカラムを「**外部キー** (FK)」と呼び、論理ER図では `FK` という略称で表記します (外部キーは、主キー以外の一意性が保証されたカラムを参照する場合もあります)。

![img](figs/06/LER-01-7.png)

論理ER図では、以下のようにカラム名の後ろに `(FK)` を付け、`user_id (FK)` のように表記することもあります。

![img](figs/06/LER-01-8.png)

このように設計することで、テーブル間の対応関係が明確になり、SQL の `JOIN` を使って関連するデータを結合して取得できます。

::: {.balloon .char-01 .face-05 .tone-blue}
言い換えれば、**他のテーブルの一意性が保証されたカラム (主に「主キー」) を参照するカラム** のことを「**外部キー**」とも呼びます。
:::

なお、リレーションの線は、テーブルを表す四角形の枠につなぐ方法のほか、上図のように <span class="masked">対応する「主キー」と「外部キー」を直接結ぶ方法</span> もあります。後者は、どのカラム間に参照関係があるのかを直感的に理解しやすいという特徴があります。

#### スキルの例に戻ってキーを決める

「繰り返しカラムは別テーブルで管理」で分離した、キャラクタとスキルの例に戻ります。今度は、**同名のキャラクタも登録できる**こと、**同じキャラクタの同じスキル枠には1つのスキルを登録する**ことを要件として、キーを決めます。

**▼ characters テーブル (下線は主キー)**

|<u>character_id</u>|name|job|
|:--:|:--:|:--:|
|1|Alice|Priest|
|2|Bob|Monk|
|3|Alice|Priest|

**▼ skills テーブル (下線の2カラムを組み合わせて主キー)**

|<u>character_id</u>|<u>slot_no</u>|skill|
|:--:|:--:|:--:|
|1|1|Heal|
|1|2|Resurrection|
|2|1|DragonKick|
|3|1|Heal|

`characters` は `character_id` を主キーにします。名前が同じ Alice でも、ID が `1` と `3` なら別のキャラクタとして区別できます。`skills` では名前ではなく、その ID を保持することで、どちらの Alice のスキルかが分かります。この **`skills.character_id` が、`characters` を参照する外部キー**です。

一方、`skills` は同じキャラクタに複数行があるので、`character_id` だけでは行を識別できません。`slot_no` だけでも、Alice と Bob がどちらも1番の枠を持つため識別できません。そこで、**`(character_id, slot_no)` を複合主キー**にします。これなら、Alice の1番の枠に Heal、2番の枠に Resurrection を保存でき、Bob にも1番の枠を設定できます。

::: {.balloon .char-01 .face-05 .tone-blue}
重複できないのは「キャラクタの ID と枠番号の組み合わせ」です。同じキャラクタでも枠番号が違えば別の行になり、別のキャラクタなら同じ枠番号を使用できます。
:::

キーまで決めた論理ER図は、次のようになります。`skills` の上部の区画にある2カラムが複合主キーで、そのうち `character_id` は外部キーでもあります。キャラクタはスキル未登録でも保存できるので、`characters` の1件に対して `skills` は **0件以上**、`skills` の1件は **必ず1件** の `characters` に属します。

### 多対多のリレーションの分割 (中間テーブル化)

RDB では、2 つのテーブル間の `多対多` となる関係を <span class="masked">直接的に定義すること</span> ができません。そのため、両者の対応関係を管理する「**中間テーブル** (**関連エンティティ)** 」というものを作成して、`1対多` と `多対1` の関係に分解して扱います。

たとえば、ブログシステムにおいて、**Article** エンティティと **Category** エンティティは `多対多` の関係にあります。つまり、1 つの記事は「<u>1 つ以上</u>の複数のカテゴリ」に属することができ、同時に、1 つのカテゴリは「<u>0 個以上</u> の複数の記事」を持つことができるという `多対多` の関係となります。

この `多対多` の関係は、「概念ER図」では以下のように表現しました。

![img](figs/06/LER-01-4.png)

- リレーションの両端の記号が「<u>0 個以上</u>」と「<u>1 つ以上</u>」で使い分けられている点に注意してください。

これを「論理ER図」に落とし込む際には **article_categories** という「中間テーブル」を作成して、次のように `1対多` と `多対1` の関係に分解します。実際の RDB でも、この構造に従ってテーブルを作成します。なお、中間テーブルの名前は任意に設定できますが、一般には <span class="masked">スネークケースで両側のエンティティ名を組み合わせた名前</span> がよく使われます。

![img](figs/06/LER-01-5.png)

中間テーブルは、2 つのエンティティの対応関係を管理するとともに、その関係に付随する情報 (＝**その組み合わせに固有の情報**) も記録する役割を持ちます。例えば **article_categories.assigned_at** は、「その記事を、そのカテゴリに分類した日時」を表します。この日時は、記事そのものやカテゴリそのものの情報ではなく、<u>特定の記事とカテゴリの組み合わせに対する情報</u> という位置づけになります。

---

ゲームにおける **character_items.quantity** (所持数) も同じ考え方です。例えば、Alice が回復薬を 3 個、Bob が回復薬を 5 個所持している場合、同じ種類のアイテムでもキャラクタによって所持数は異なります。また、Alice が所持するアイテムであっても、その種類によって所持数は異なります。

つまり、`quantity` はキャラクタだけでもアイテムの種類だけでも決まるものではなく、両者の組み合わせによって決まる情報であるため、それは両者の対応関係を管理する中間テーブル `character_items` に記録するという考え方になります。

![img](figs/06/LER-02-5.png)

#### 📝演習4

ある書籍小売店では、書籍や著者、出版社、仕入れ履歴を管理するため、次の 5 つのテーブルからなるデータベースを使用しています。以下の説明を読み、**IE記法 (Crow's Foot記法) による論理ER図を作成**してください。

ここでいう「書籍」は、個々の現物ではなく、タイトルや価格などを管理する単位を表します。同じ書籍を複数冊仕入れた場合は、仕入れ履歴の数量に冊数を記録します。

**(テーブルの構成とビジネスルール)**

1. **authors (著者)**
    - 著者を管理します。カラムは、著者ID **author_id**、著者名 **name**、国コード **country_code**、生年月日 **birthday** の4つです。**author_id** を主キーとします。
2. **publishers (出版社)**
    - 出版社を管理します。カラムは、出版社ID **publisher_id**、出版社名 **name**、郵便番号 **zip_code** の3つです。**publisher_id** を主キーとします。
3. **books (書籍)**
    - 書籍を管理します。カラムは、書籍ID **book_id**、書名 **title**、価格 **price**、印刷部数 **print_run**、発売日 **release_date**、出版社ID **publisher_id** の6つです。**book_id** を主キーとし、**publisher_id** は **publishers** の **publisher_id** を参照する外部キーとします。
    - 1件の書籍に設定できる出版社は、0件または1件です。出版社が未設定の場合、**publisher_id** は **NULL** とします。一方、1つの出版社に対応する書籍は0件以上で、書籍がまだ登録されていない出版社も登録できます。
4. **book_authors (書籍と著者の対応関係)**
    - どの書籍をどの著者が執筆したかを管理します。カラムは、書籍ID **book_id**、著者ID **author_id**、著者の記載順 **author_order** の3つです。**book_id** と **author_id** の組み合わせを複合主キーとします。**book_id** は **books** の **book_id** を、**author_id** は **authors** の **author_id** を参照する外部キーとします。
    - 1行は、必ず1件の書籍と1人の著者の対応を表します。1件の書籍に対応する **book_authors** の行は0行以上で、1人の著者に対応する行も0行以上です。同じ書籍に複数の著者を登録でき、同じ著者を複数の書籍に登録することもできます。また、著者との対応がまだない書籍や、書籍との対応がまだない著者も登録できます。
    - **author_order** は、その書籍での著者の記載順を表します。たとえば、ある書籍で先頭に記載する著者は1、2番目の著者は2とします。
5. **book_purchases (仕入れ履歴)**
    - ある書籍を、いつ、何冊仕入れたかを管理します。カラムは、仕入れID **id**、書籍ID **book_id**、仕入れ冊数 **qty**、仕入れ日時 **purchased_at** の4つです。**id** を主キーとし、**book_id** は **books** の **book_id** を参照する外部キーとします。
    - 1件の仕入れ履歴は、必ず1件の書籍に対応します。1件の書籍に対応する仕入れ履歴は0件以上です。同じ書籍を別の機会に仕入れた場合は、別の **id** を持つ行として記録します。仕入れ履歴がまだない書籍も登録できます。

#### 共通の指示事項

- 一般的に IE記法 (Crow's Foot記法) と言える範疇のものであればスタイルは自由に決定し、エンティティ配置や PK・FK の表記法など、論理構造に影響しない要素は任意に決めてください。一般的とは言えない (あるいは判断に迷う) 記号・表記・略称を使う場合や、色や線の種類に特別な意味を持たせる場合は、読み手が意味を取り違えないよう、図の中に凡例（注釈）を添えてください。凡例には、使った記号や表記と、その意味の対応を書いてください。凡例を添えたことによる減点はありません。
  - 特に **_演習1_** と **_演習2_** について、エンティティの配置などを必ずしも見本と一致させる必要はありません。
- <u>論理構造が正しいこと (適切であること)</u>および<u>図として読みやすく整っていること</u>が評価の観点となります。
- **_演習3・4_** については、文章で指定されたテーブル構造と関係が正確に表現されていることが主な評価の観点となります。また、図として読みやすく整っていることも重視し、主キーと外部キーの対応が線の接続位置から読み取れることもボーナス要素にします。
