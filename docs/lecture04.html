4 ORDER BY 句

前回講義では、SQL の SELECT 文を使用して「テーブルからレコードを取得する方法」について学びました。その際、取得結果のレコードの ならび (順番) は、おそらく id カラムの昇順になっていたと思います。

実際に、sql/04/tmp.sql に以下の SQL 文を記述し、実行して結果を確認してください。

SET
  search_path TO w03;

SELECT
  id,
  guild AS "所属ギルド",
  name AS "名前",
  level AS "レベル",
  TO_CHAR(last_login_at, 'YYYY"/"MM"/"DD HH24":"MI') AS "最終ログイン"
FROM
  characters;

ここで押さえておくべき「SQLの重要な特性」があります。

SQL は「集合指向」の言語であり、「idカラムの昇順」あるいは「レコードが挿入(INSERT)された順」でレコードが得られるというのは 「たまたま」の結果 に過ぎません。実際には、取得結果のレコード (これを一般に「結果セット (result set)」とよびます) の「ならび (順序)」は 不定である (論理的に保証されるものではない) ということを覚えておいてください。

そこで、指定した条件に従って結果セットを整列する仕組みとして、SELECT 文には、ORDER BY句 というものが用意されています。

  • PostgreSQL では ORDER BY を指定しない限り、SELECT 文の結果セットにおけるレコードの順序は保証されないと学びました。しかし、実際に同じ SELECT 文を何度実行しても、毎回同じ順番で表示されます。具体的にどのような操作や状況によって、レコードの順序が変わる可能性があるのですか。

中級者向け: 補足

PostgreSQLはデータを ヒープファイル（Heap File） で管理しており、新しく追加された行は、通常、テーブル内の空きページや末尾のブロックに順次追加されます。そのため、テーブルスキャン (順次読み出し) を行うと、挿入順に近い順序で読み込まれることがよく起こります。ただし、UPDATE による行の更新、VACUUM FULL によるテーブルの書き直し、インデックススキャンの使用、並列処理などによって、取得結果の順序は変わることがあります。

そのため、SELECT 文の結果が、INSERT の順番に並ぶという挙動は「たまたま」そう見えているに過ぎず、結果セットのレコード順序を意図的に制御したい場合は必ず ORDER BY 句を使用する必要があります。

  • ここでの ヒープファイル とは、アルゴリズムやデータ構造で学んだ ヒープ構造 (二分ヒープなど) とは全く別物です。データを「積み上げる（Heap）」ことに由来する用語で、特定のデータ構造を指すものではないので注意してください。
  • PostgreSQL における VACUUM とは何ですか。

4.1 ORDER BY 句

ORDER BY は、SELECT 文において、結果セットのレコードの「ならび (順序)」を指示するもので (＝整列順・ソート順 を指示するもので)、以下のように FROM 句 より後に記述します。

ORDER BY が指定するのは、取得結果のならびであり、元のテーブルのデータを、この順序に並べ替えて保存するわけではない ので注意してください。

SET
  search_path TO w03;

SELECT
  id,
  guild AS "所属ギルド",
  name AS "名前",
  level AS "レベル",
  TO_CHAR(last_login_at, 'YYYY"/"MM"/"DD HH24":"MI') AS "最終ログイン"
FROM
  characters
ORDER BY -- ◀ ここに注目
  guild;
  • SELECT 文は、SELECT 句 👉 FROM 句 👉 ORDER BY 句 という順序で記述しないと構文エラーになるので注意してください。

上記の SQL の実行結果 ( ORDER BY guild の結果) は、「所属ギルド」を基準に整列されます。以下に実行結果の一例を示します。文字列の具体的な整列順は、後述する「照合順序」の設定によって変わる場合があります。

ここでは、所属ギルドの順序だけを指定しています。

同じギルドに所属するキャラクタ同士のならびは、まだ指定していません。ギルド内のならびも指定する方法は、このあとの「複数のソートキーの指定」で説明します。

ORDER BY は、デフォルトで ASC (＝ 昇順) で整列 (ソート) します。数値型なら「小さい順」、日時型なら「古い順」になります。

降順に整列したい場合は、ORDER BY guild DESC のように DESC キーワード を指定します。

  • 昇順であることを明示したい場合は ORDER BY guild ASC のようにします。
  • PostgreSQL では、昇順 ( ASC ) で整列した場合、NULL 値は 最後に配置 されることに注意してください。
  • 文字列の整列順は、データベースなどに設定された 照合順序 (Collation) によって決まります。そのため、必ずしも「大文字の A-Z が先、小文字の a-z が後」という順序で並ぶとは限りません。
    • 大文字と小文字を区別せずに整列したい場合は、ここでは ORDER BY LOWER(guild) のように、小文字に変換した値を整列の基準にします。

中級者向け: 演習環境における照合順序 (文字列の整列順) の確認

PostgreSQL においては、照合順序は、文字列型のカラムごとに設定することができます。カラムに個別の指定がなければ、データベース既定の照合順序が使用されます。

実際に、ORDER BY guild に適用される照合順序と、それによる文字列の整列順を確認してみます。sql/04/temp.sql に次の SQL を記述し、実行してみてください。最後の VALUES は、確認用の文字列を用意するための記法となります。

SELECT DISTINCT COLLATION FOR (guild) AS collation
FROM w03.characters;

SELECT datcollate
FROM pg_database
WHERE datname = current_database();

SELECT word
FROM (VALUES ('b'), ('A'), ('a'), ('B'),
             ('い'), ('ぃ'), ('あ'), ('ぁ'),
             ('が'), ('か'), ('ぱ'), ('ば'), ('は'),
             ('山田'), ('田中')) AS sample(word)
ORDER BY word;

最初の結果は "default" となり、これより guild カラムにはデータベース既定の照合順序が適用されていることが確認できます。

つづいての結果は ja_JP.UTF-8 であり、この演習環境における、データベース既定の照合に使用するロケールが ja_JP.UTF-8 であることが確認できます。

最後の SQL で、ja_JP.UTF-8 による整列順を確認しています。これより以下のようなことがわかると思います。

  • アルファベット: 大文字の A〜Z が先、そのあとに小文字の a〜z がならびます。
  • ひらがな: 小さい文字と通常の文字は、「ぁ」👉「あ」👉「ぃ」👉「い」の順で並びます。濁点・半濁点を含む例では、「か」👉「が」、「は」👉「ば」👉「ぱ」の順で並びます。
  • 漢字: より複雑で、単純に読みの五十音順にはなりません。この環境では「山田」が「田中」より先になります。なお、単純な UTF-8 の文字コード順になるわけではないことに注意してください。

漢字氏名を読み順にならべたい場合は、「ふりがな」のカラムを別に用意し、その値を基準に整列することが一般的となります。

4.2 複数のソートキーの指定

ORDER BY 句では、カンマ で区切って、第1ソートキー、第2ソートキー、第3ソートキー…と複数のソートキーが指定できます。例えば、まず 所属ギルドのABC順 (昇順) で整列 し、さらに 所属ギルドのなかでレベルが高い順 (降順) に整列 したい場合は、次の 第12行目 のように ORDER BY 句を記述します。

SET
  search_path TO w03;

SELECT
  id,
  guild AS "所属ギルド",
  name AS "名前",
  level AS "レベル",
  TO_CHAR(last_login_at, 'YYYY"/"MM"/"DD HH24":"MI') AS "最終ログイン"
FROM
  characters
ORDER BY -- ◀ ここに注目
  guild,
  level DESC;

ソートキーは、左から順に優先されます。この例では、まず guild で整列し、guild の値が同じレコード同士を、level の降順で整列します。

  • 明示的に ORDER BY guild ASC, level DESC; としても同様の結果となります。
  • ASC や DESC は、それぞれのソートキーに対して指定します。ORDER BY guild, level DESC の DESC が適用されるのは、level だけです。

4.3 NULL 値のソート位置を指定

先のセクションで確認したように、PostgreSQL において ORDER BY に ASC (昇順) を指定したときは NULL 値は最後に配置されます。逆に DESC (降順) を指定したときは NULL 値が先頭に配置されます。

NULLS FIRST・NULLS LAST を 省略した場合 の NULL の位置は、DBMS (PostgreSQL, MySQL, SQLite, Oracle etc.) によって異なります。これは 実装依存 (implementation-dependent) であり、使用する DBMS の仕様によって決まるという意味です。

標準 SQL (および PostgreSQL を含む多くの実装) では、ORDER BY による整列で NULL の位置を明示的に指定するために NULLS LAST と NULLS FIRST というキーワードが使用できます。

例えば、次のように記述することで、最終ログイン日時が新しい順 (降順 DESC) に並べつつ、NULL 値のレコードを「最後」に配置することができます。

SET
  search_path TO w03;

SELECT
  id,
  name,
  last_login_at
FROM
  characters
ORDER BY
  last_login_at DESC NULLS LAST; -- ◀ ここに注目

NULLS FIRST・NULLS LAST は、各ソートキーの ASC・DESC の 後ろ に記述してください。例えば、ORDER BY LOWER(guild) ASC NULLS FIRST, level ASC では、ギルドが NULL のレコードを先頭にまとめ、そのなかではレベルの昇順に整列します。

  • 上記の 第11行目 を last_login_at DESC; に書き換えると、last_login_at が NULL のレコードが先頭に配置されることを確認してください。

4.4 CASE式を使用したORDER BY句の指定

前回講義では、SELECT 句のなかで CASE式 を利用する方法を紹介しました。CASE 式は SELECT 句だけではなく ORDER BY 句のなかでも使用することができます。

SQL文のなかで「式」を記述できる場所であれば、どこでも CASE 式を記述することができます。

例えば、jobカラムについて、「後衛職」👉「前衛職」の順に整列し、さらに、それぞれのなかでは「ABC順」にジョブ (職業) を整列し、さらにレベル (降順) で整列したい場合は、次のように ORDER BY 句のなかで CASE 式を利用します。

  • 後衛職: Priest、Wizard
  • 前衛職: Fighter、Monk、Ninja、Samurai
SET
  search_path TO w03;

SELECT
  id,
  name,
  job,
  level
FROM
  characters
ORDER BY
  CASE
    WHEN job = 'Priest' OR job = 'Wizard' THEN 1
    ELSE 2
  END ASC, -- CASE式による第1キー
  job, -- 第2キー
  level DESC; -- 第3キー

ここでは、第12行目 から 第15行目 にかけての CASE 式で後衛職に数値の「1」、それ以外 (前衛職) に数値の「2」を割り当て、それを第1キーとして昇順 (ASC) に整列しています。つまり、ジョブ (文字列型) を数値型にマッピングして、それを整列のキーに使用しています。

この CASE 式が返す「1」「2」は整列のために使用され、結果セットには表示されません。元の job カラムの値も変更されません。

  • 第13行目 は、IN キーワードを使用して WHEN job IN ('Priest', 'Wizard') THEN 1 のように記述することもできます。

5 LIMIT 句

SQL では、LIMIT を使用して 取得するレコードの上限 を設定することができます。

  • SELECT 文は、SELECT 句 👉 FROM 句 👉 ORDER BY 句 👉 LIMIT 句 という順で記述しないと構文エラーになるので注意してください。

例えば、レベルの高い順に整列して「上位5件」のレコードを取得する場合、次のように SQL を記述します。

SET
  search_path TO w03;

SELECT
  id,
  name,
  level
FROM
  characters
ORDER BY
  level DESC
LIMIT -- ◀ ここに注目
  5;

LIMIT 30 のように、全レコード数よりも大きな値を指定するとどのようになるか、実際に確認してください。

5.1 LIMIT の利用上の注意点

LIMIT 句は単独でも使用できますが、実務では ORDER BY 句と組み合わせて使うことが基本となります。ORDER BY 句なしで LIMIT 句を使用すると、その結果セットの内容は「不定」となります。

  • ORDER BY なしでも毎回同じ結果セットが得られるように見えることがありますが、それは 偶然にすぎず、保証された動作ではありません。

実運用では、VACUUM FULL によるテーブルの書き直しや UPDATE、インデックスの利用状況、並列実行の影響などで、取得されるレコードの順序が変化する可能性があり、そこから上位 N 件分を取得する LIMIT の結果も変わります。

意図的に「N 件のレコードをランダムに取得したい」という場合には、次のように ORDER BY RANDOM() と LIMIT を併用します。

SET
  search_path TO w03;

SELECT
  id,
  name,
  level
FROM
  characters
ORDER BY
  RANDOM() -- ◀ ここに注目
LIMIT
  5;

これにより、ランダムに5件のレコードを取得すること ができます。

ORDER BY を指定しても、同値の行同士の順序には注意

ORDER BY level DESC のように整列していても、同じレベルのレコード同士の順序は保証されないので注意してください。そのため、同値のレコードがページの境界をまたぐ場合、ページごとに取得すると、同じレコードが重複したり、一部のレコードを取得し損ねたりする可能性があります。

  • 同じデータに対して順序を一意に定めるには、ORDER BY level DESC, id ASC のように、主キーの id など一意な値を持つカラムを最後のソートキーに追加します。

より詳しく知りたい人は PostgreSQL 18 公式資料の「SELECT」の ORDER BY Clause と LIMIT and OFFSET を参照してください。前者にはすべてのソートキーが同値の場合の扱い、後者には順序を一意に定める必要性が説明されています。

  • PostgreSQL で ORDER BY level DESC でレベル順にしてから、LIMIT と OFFSET で5件ずつ取得しています。同じレベルの人が何人かいると、前のページと同じ人が出てくることもあるそうです。データを追加も削除もしていないのに、どうしてそんなことが起こるんですか？

  • PostgreSQL で ORDER BY RANDOM() LIMIT 5 とすると、ランダムに5件取得できました。5件だけ選ぶのに、テーブル全体をならべ替えているんですか。それとも、レコードが1000万件あっても、5件だけならすぐに取得できるんでしょうか？

5.2 OFFSET 句

LIMIT と OFFSET を組み合わせて使用することで「ページング処理 (ページネーション)」を行なうことができます。たとえば、ある結果セットについて「101件目から150件目」だけを取得したいとき、LIMIT 50 OFFSET 100 のように利用することができます。OFFSET 100 は先頭の100件を読み飛ばす指定であり、その次の101件目から、最大50件を取得します。

ただし、OFFSET で読み飛ばす行も、サーバ内部では処理する必要があります。そのため、大きなオフセット値は処理負担が増える原因になります。

  • 例えば、同じ条件で LIMIT 50 OFFSET 100 と LIMIT 50 OFFSET 10000 を比較すると、一般的には後者のほうが処理負担が大きくなります。ただし、実際のレスポンスタイムはデータや実行計画などにも左右されます。

大きなオフセット値による応答時間の増加が問題になる場合は、「カーソルページネーション (キーセットページネーション)」という手法も検討します。

これは、最後に表示したレコードのキーを基準に、その次のレコードから取得する手法です。例えば、id の昇順で次のページへ進む場合は、WHERE id >【最後に表示したID】 ORDER BY id ASC LIMIT 50 のように記述します。降順で進む場合は、WHERE id <【最後に表示したID】 ORDER BY id DESC LIMIT 50 となります (WHERE 句は、このあとのセクションで説明します)。

この手法は、整列順と検索条件に合ったインデックス (詳細は次回以降に説明) を利用できる場合、大きな OFFSET による処理負担を抑えることができます。採用するかどうかは、レコード数だけでなく、取得条件や実際の応答時間を踏まえて判断します。

ただし、カーソルページネーションは、前のページの最後のキーを基準にするため、特定のページ番号に直接ジャンプすることができない というデメリットがあります。

以下に「レベルの降順で整列して、11件目から15件目にあたるレコードを取得する SQL」を示します。

SET
  search_path TO w03;

SELECT
  id,
  name,
  level
FROM
  characters
ORDER BY
  level DESC
LIMIT
  5
OFFSET -- ◀ ここに注目
  10;
  • LIMIT 5 OFFSET 10 は、順番を入れ替えて OFFSET 10 LIMIT 5 としても問題ありません (構文エラーにはなりません)。
    • ただし、一般的には LIMIT ... OFFSET ... で記述します。PostgreSQL の公式ドキュメントでも、この順序で記載されています。

  • ウェブアプリに関する文脈で「ページング処理」とはなんですか。

  • RDBに関する文脈で「カーソルページネーション」とは何ですか。

  • RDBに関する文脈で「インデックス」とは何ですか。「カーソルページネーションは、整列順と検索条件に合ったインデックスを利用できると、大きな OFFSET を与えたときの処理負担を抑えることができます」と言われたのですが、どういうことですか？

  name,

FROM

6.2 SQLの3値論理

SQL では TRUE と FALSE に加えて、「不明・未知」を表す UNKNOWN を扱う 3値論理 (Three-Valued Logic、3VL) が採用されています。UNKNOWN は、比較や論理演算などで 真偽を判定できない状態 を表します。PostgreSQL では、真偽値の不明は BOOLEAN 型の NULL で表されます。

たとえば level = NULL や last_login_at = NULL などの比較式を評価すると、結果は UNKNOWN となります。一方、level + NULL の計算結果は INTEGER 型の NULL であり、真偽値の UNKNOWN とは区別します。

  • IS NULL や IS NOT NULL は特別に真偽を判定できる例外的な存在です。

この UNKNOWN が混ざると、論理演算 (AND・OR・NOT) の結果も UNKNOWN を含む形で評価されることに十分に注意してください。

教科書の pp.76-77 の「NULL を含む場合の真理値」も参照してください。

3値論理の「論理否定」は次のようになります。

A NOT A
TRUE FALSE
FALSE TRUE
UNKNOWN UNKNOWN

SELECT

6.2.2 SQLの3値論理の論理積 (AND)

3値論理の「論理積 (AND)」は次のようになります。

A B A AND B
TRUE TRUE TRUE
TRUE FALSE FALSE
TRUE UNKNOWN UNKNOWN
FALSE TRUE FALSE
FALSE FALSE FALSE
FALSE UNKNOWN FALSE
UNKNOWN TRUE UNKNOWN
UNKNOWN FALSE FALSE
UNKNOWN UNKNOWN UNKNOWN

UNKNOWN を含まないときは、従来の2値論理 (TRUE/FALSE) の 論理積 (AND) と同じ結果となります。一方、UNKNOWN が含まれる場合は、次のように考えます。

  • TRUE AND UNKNOWN の演算結果は、以下のようにどちらの結果にもなり得るため、UNKNOWN と考えます。
    • 仮に UNKNOWN が TRUE であれば TRUE AND (TRUE) 👉 TRUE
    • 仮に UNKNOWN が FALSE であれば TRUE AND (FALSE) 👉 FALSE
  • FALSE AND UNKNOWN の演算結果は、以下のように常に FALSE になるため、FALSE と考えます。
    • 仮に UNKNOWN が TRUE であれば FALSE AND (TRUE) 👉 FALSE
    • 仮に UNKNOWN が FALSE であれば FALSE AND (FALSE) 👉 FALSE

次の SQL を実行して実際に確認してみてください。

SELECT
  True AND Null AS "True AND Unknown",
  False AND Null AS "False AND Unknown",
  Null AND Null AS "Unknown AND Unknown";

3値論理の「論理和 (OR)」は次のようになります。

A B A OR B
TRUE TRUE TRUE
TRUE FALSE TRUE
TRUE UNKNOWN TRUE
FALSE TRUE TRUE
FALSE FALSE FALSE
FALSE UNKNOWN UNKNOWN
UNKNOWN TRUE TRUE
UNKNOWN FALSE UNKNOWN
UNKNOWN UNKNOWN UNKNOWN

UNKNOWN を含まないときは、従来の2値論理 (TRUE/FALSE) の 論理和 (OR) と同じ結果となります。一方、UNKNOWN が含まれる場合は、次のように考えます。

  • TRUE OR UNKNOWN の演算結果は、以下のように常に TRUE になるため、TRUE と考えます。
    • 仮に UNKNOWN が TRUE であれば TRUE OR (TRUE) 👉 TRUE
    • 仮に UNKNOWN が FALSE であれば TRUE OR (FALSE) 👉 TRUE
  • FALSE OR UNKNOWN の演算結果は、以下のようにどちらの結果にもなり得るため、UNKNOWN と考えます。
    • 仮に UNKNOWN が TRUE であれば FALSE OR (TRUE) 👉 TRUE
    • 仮に UNKNOWN が FALSE であれば FALSE OR (FALSE) 👉 FALSE

6.3 WHERE句でよく利用する述語

SQLにおいて、TRUE・FALSE・UNKNOWN のいずれかに評価される条件式を 述語 (Predicate) といいます。代表的なものとして…

  • 比較述語 (比較演算子)
  • NULL判定述語
  • IN述語 (IN演算子)
  • LIKE述語 (LIKE条件、パターンマッチ演算子)
  • BETWEEN述語 (BETWEEN条件、範囲演算子)

…があります。実務では、括弧内の表記で呼ばれることが多いです。

  • 比較演算子: =（等しい）、<（より小さい）、<=（以下）、>（より大きい）、>=（以上）、<>（等しくない）など。
    • PostgreSQL のほか、様々な RDBMS で <> の代わりに != を不等価演算子として使用することができます。ただし、標準 SQL で定められているのは <> のほうなので、原則として <> を使用してください。
  • NULL判定述語: IS NULL、IS NOT NULL など。
    • NULL判定には = NULL ではなく、必ず IS NULL を使用してください。= NULL の評価結果は、常に UNKNOWN となります。
    • PostgreSQL では、ISNULL と NOTNULL を使用することもできます。

6.3.1 IN述語 (IN演算子)

ジョブが「Priest」または「Wizard」のレコードを抽出する SQL は、IN演算子 を使用して次のように記述することができます。条件としては job = 'Priest' OR job = 'Wizard' と同じですが より簡潔に記述できるメリット があります。

SET
  search_path TO w03;

SELECT
  *
FROM
  characters
WHERE
  job IN ('Priest', 'Wizard');

なお、文字列の比較は、大文字と小文字を区別するので注意してください。job IN ('priest', 'wizard') のようにすると、抽出されるレコードは「0件」 になります。

また、IN は、論理否定の NOT と組み合わせることができます。たとえば、Priest と Wizard 以外のジョブ (つまり、Fighter、Monk、Ninja、Samurai) を抽出する SQL は次のように記述できます。

SET
  search_path TO w03;

SELECT
  *
FROM
  characters
WHERE
  job NOT IN ('Priest', 'Wizard');

ここでは NOT job IN ('Priest', 'Wizard') のように記述しても、条件の意味と結果は同じです。ただし、本科目では、否定の対象が読み取りやすい job NOT IN ('Priest', 'Wizard') の記法を使用してください。

なお、WHERE 句で NOT IN を使用するとき、リストに NULL を含むと、評価結果は FALSE または UNKNOWN となり、1件のレコードも抽出されなくなるので注意してください。例えば、ギルドが、Yamato、無所属 (NULL) 以外 のレコードを抽出したいとき、次の SQL では意図した結果が得られません。実際に確認してみてください。

SET
  search_path TO w03;

SELECT
  *
FROM
  characters
WHERE
  guild NOT IN ('Yamato', NULL); -- Yamato と NULL 以外を抽出したい

この例では、guild が Yamato のレコードは FALSE、それ以外のギルドや NULL のレコードは UNKNOWN となります。TRUE となるレコードがないため、結果は0件になります。意図した条件は、WHERE guild <> 'Yamato' AND guild IS NOT NULL と記述できます。

  • PostgreSQL で、NOT job IN ('Priest', 'Wizard') と job NOT IN ('Priest', 'Wizard') は同じ結果になると学びました。それぞれの条件の意味と、後者のほうが否定の対象を読み取りやすい理由を説明してください。

  • SQLに関する質問です。あるテーブルにギルドというカラムがあります。いま、ギルドのカラム値が Yamato または NULL 以外のレコードを抽出したいです。そのために guild NOT IN ('Yamato', NULL) のように、WHERE句を書いたのですが、意図した結果がえられません。なぜ、このようなことが起きますか。

6.3.2 LIKE述語 (LIKE条件、パターンマッチ演算子)

キャラクタの名前が「C」から始まるようなレコードを抽出したいときは、LIKE 条件を使用し、次のように SQL を記述します。

SET
  search_path TO w03;

SELECT
  *
FROM
  characters
WHERE
  name LIKE 'C%';

ここで % (＝ワイルドカード) は 0文字以上の任意の文字列 を表し、C% は、大文字の「C」から始まる任意の文字列 (「C」だけの1文字の文字列を含む) を表現しています。そのため、WHERE name LIKE 'C%' では、name カラムが「Charlie」「Carol」「Chaplin」のようなレコードだけが抽出されます。

なお、大文字と小文字を区別するので、name が「chris」のレコードは抽出されません。小文字を含めて抽出したいときは UPPER(name) LIKE 'C%' のようにします。

  • 特定の文字で終わるレコードを抽出したいとき (後方一致検索) は、ワイルドカード % を前に置きます。例えば「セルゲエビッチ」「ミハイロビッチ」「ペトロビッチ」のように「ビッチ (vich) 」で終わる名前のレコードを抽出したいときは name LIKE '%vich' のようにします。
  • 特定の文字を含むレコードを抽出したいとき (中間一致検索) は、ワイルドカード % を検索文字列の前後に配置します。たとえば、dra を含む名前を抽出したいときは LOWER(name) LIKE '%dra%' のようにします。
    • Dracula (ドラキュラ)、Cendral (センドラル)、Hydra (ハイドラ) などがマッチします。
  • PostgreSQL の LIKE で、% は0文字以上の任意の文字列を表すと習いました。それなら guild LIKE '%' は、ギルド名が何であっても一致するんですか。NULL や、何も文字が入っていない空文字列 '' も一致するのでしょうか？

6.3.3 BETWEEN述語 (BETWEEN条件、範囲演算子)

「XX 以上 YY 以下」のような範囲条件でレコードを抽出したいときは、BETWEEN を使うことで簡潔に WHERE 句を記述することができます。

例えば、level が 20以上39以下 のレコードを抽出したい場合、次のように SQL を記述することができます。

SET
  search_path TO w03;

SELECT
  *
FROM
  characters
WHERE
  level BETWEEN 20 AND 39;

この条件は WHERE level >= 20 AND level <= 39 と同じ意味になりますが、BETWEEN を使うほうが可読性に優れています。なお、BETWEEN は 両端の値を含むこと に注意してください。上記の例では、レベルが 39 のレコードも 含まれます。

  • Python の range(20,39) のように上限を除外する仕様とは異なるため、混同しないように注意してください。

BETWEEN は、特に DATE 型や TIMESTAMP 型のカラムでよく使用されます。例えば、最終ログイン日時 (TIMESTAMP型) が「2025-07-01」から「2025-07-31」までの範囲にあるレコードを抽出したいときは次のように記述します。

SET
  search_path TO w03;

SELECT
  id,
  name,
  last_login_at
FROM
  characters
WHERE
  last_login_at BETWEEN '2025-07-01 00:00:00' AND '2025-07-31 23:59:59.999999'
ORDER BY
  last_login_at;
  • 注意: WHERE last_login_at BETWEEN '2025-07-01' AND '2025-07-31' とすると、last_login_at が 2025年7月31日 10時15分 のようなレコードが選択されないので注意してください。
    • なお、last_login_at が、created_on のように時刻を含まない DATE 型であれば、この問題は生じません。
  • PostgreSQL に関する質問です。last_login_at という TIMESTAMP 型のカラムがあります。このとき、WHERE last_login_at BETWEEN '2025-07-01' AND '2025-07-31' では、2025-07-31 10:15:00 のようなレコードが選択されないのはなぜですか。

さらに、前回講義 で紹介した DATE_PART 関数と組み合わせることで、最終ログインが「9時台から17時台」のレコードを抽出するようなこともできます。

SET
  search_path TO w03;

SELECT
  id,
  name,
  last_login_at
FROM
  characters
WHERE
  DATE_PART('hour', last_login_at) BETWEEN 9 AND 17
ORDER BY
  CAST(last_login_at AS TIME); -- 時刻で整列
  • DATE_PART('hour', last_login_at) は、時の部分を0〜23の数値として返します。戻り値の型は INTEGER ではなく DOUBLE PRECISION です。BETWEEN 9 AND 17 は「9時台〜17時台の間」を意味します (17時台の終わりまでを含むことに注意してください)。

6.3.4 定着確認

  • w03.characters テーブルの job は VARCHAR 型である。ジョブが Priest または Wizard のレコードを取得するための WHERE 句を、IN を使用して記述せよ。
    • 答え: WHERE job IN ('Priest', 'Wizard')
  • w03.characters テーブルの guild は VARCHAR 型で、未所属の場合は NULL となる。Yamatoにも所属せず、未所属でもないレコードを取得するために WHERE guild NOT IN ('Yamato', NULL) と記述した。この条件が意図どおりにならない理由を説明し、正しい WHERE 句を記述せよ。
    • 答え: YamatoのレコードではFALSE、それ以外のギルドやNULLのレコードではUNKNOWNとなり、TRUEになるレコードがないため。正しい条件は WHERE guild <> 'Yamato' AND guild IS NOT NULL。
  • w03.characters テーブルの name は VARCHAR 型である。英字の大文字と小文字を区別せず、名前が「C」または「c」から始まるレコードを取得する WHERE 句を、UPPER と LIKE を使用して記述せよ。
    • 答え: WHERE UPPER(name) LIKE 'C%'。% は0文字以上の任意の文字列を表すため、「C」や「c」だけの名前も条件に一致する。
  • あるテーブルの level は INTEGER 型で、19・20・39・40・NULL の値を持つレコードが存在する。WHERE level BETWEEN 20 AND 39 と指定したとき、どの値を持つレコードが結果セットに含まれるか答えよ。
    • 答え: 20と39。BETWEENは両端を含む。19と40は範囲外であり、NULLの場合はUNKNOWNとなるため含まれない。
  • characters テーブルの last_login_at は TIMESTAMP 型である。2025年07月01日から07月31日の終わりまでのレコードを取得するために WHERE last_login_at BETWEEN '2025-07-01' AND '2025-07-31' と記述した。この条件では7月31日の日中が含まれない理由を説明し、秒の小数部も取りこぼさない WHERE 句に書き換えよ。
    • 答え: 上限が2025-07-31 00:00:00として解釈されるため。WHERE last_login_at >= '2025-07-01' AND last_login_at < '2025-08-01' とする。
  • characters テーブルの last_login_at は TIMESTAMP 型である。WHERE DATE_PART('hour', last_login_at) BETWEEN 9 AND 17 と指定したとき、最終ログイン日時が「2025-07-31 17:59:59.5」のレコードと「2025-07-31 18:00:00」のレコードは、それぞれ条件に一致するか。また、DATE_PART の戻り値の型も答えよ。
    • 答え: 17:59:59.5は時の部分が17なので一致し、18:00:00は18なので一致しない。戻り値の型はDOUBLE PRECISION。

6.4 CASE式を使用したWHERE句の指定

CASE 式は、WHERE 句でも利用することができます (先にも述べましたが、式を記述できる場所であれば、どこでも CASE 式を利用することができます)。

たとえば、ギルドに所属している場合はレベル 60 以上、未所属の場合はレベル 30 以上 のレコードを抽出したいとき、次のように SQL を記述することができます。

SET
  search_path TO w03;

SELECT
  id,
  name,
  guild,
  level
FROM
  characters
WHERE -- ◀ ここに注目
  level >= CASE
    WHEN guild IS NOT NULL THEN 60
    ELSE 30
  END
ORDER BY
  level DESC;

この例では、CASE 式がギルドへの所属状況に応じて「60」または「30」を返します。その値を比較の基準として、level >= 60 または level >= 30 の条件でレコードを抽出しています。

これは、次のように記述することもできます。

SET
  search_path TO w03;

SELECT
  id,
  name,
  guild,
  level
FROM
  characters
WHERE
  CASE
    WHEN guild IS NOT NULL AND level >= 60 THEN TRUE
    WHEN guild IS NULL AND level >= 30 THEN TRUE
    ELSE FALSE
  END
ORDER BY
  level DESC;

この例では、CASE 式そのものが TRUE または FALSE を返します。その真偽値を WHERE 句の条件として使用し、TRUE となるレコードだけを抽出しています。

また、CASE 式を使用せずに、次のように記述することもできます。

SET
  search_path TO w03;

SELECT
  id,
  name,
  guild,
  level
FROM
  characters
WHERE
  (guild IS NOT NULL AND level >= 60 ) OR
  (guild IS NULL AND level >= 30 )
ORDER BY
  level DESC;

7.1 トランザクションとロールバックの利用

INSERT 文の動作を実際に試しながらも、追加したレコードを残さないようにするため、ここでは明示的にトランザクションを開始し、レコードの挿入と、その確認を行った後に、ロールバックによって挿入を取り消す という手順をとります。

トランザクションの詳しい仕組みは今後の授業で扱います。ここでは、START TRANSACTION のあとに挿入したレコードを、最後の ROLLBACK で取り消します。途中の SELECT では追加したレコードを確認できますが、変更はまだ確定していません。

具体的には、次の SQL によってレコードの挿入を試しつつ、最後にロールバックによって挿入したレコードを取り消すことができます。

SET
  search_path TO w03;

-- トランザクションを開始
START TRANSACTION;

-- レコードの挿入
INSERT INTO
  users (id, name, age)
VALUES
  (3, 'Carol', 18);

-- 結果の確認
SELECT * FROM users;

-- このトランザクションで挿入したレコードを取り消し (ロールバック)
ROLLBACK;

上記の SQL を実行してみてください。次のような結果が得られるはずです。

 id | name  | age
----+-------+-----
  1 | Alice |  20
  2 | Bob   |  25
  3 | Carol |  18

つづいて、ロールバックによって「Carol」のレコードの挿入が取り消されていることを確認してみます。

(START TRANSACTION ～ ROLLBACK で囲まずに) SELECT * FROM w03.users; を実行してみてください。ロールバックにより、「Carol」のレコードの挿入は取り消され、テーブルのレコードは元の2件に戻っているはず です。

 id | name  | age 
----+-------+-----
  1 | Alice |  20
  2 | Bob   |  25

今後しばらくは、レコードを挿入する INSERT 文、レコードを削除する DELETE 文、レコードを更新する UPDATE 文などは START TRANSACTION ～ ROLLBACK の範囲内で試すようにしてください。

なお、第17行目の ROLLBACK を COMMIT に置き換えると、変更内容が確定し、その後も追加したレコードが残ります（今回はあくまで練習なので、最後は ROLLBACK にしてください）。

自動採番の番号はロールバックで戻りません

ここまでの w03.users では id を手動で指定しましたが、このあとのドリルで使用する w03.characters では id が自動採番されます。自動採番の番号は、ロールバックしても元に戻りません。同じ演習を繰り返すと番号が飛ぶことがありますが、挿入したレコードが残ったという意味ではありません。

  • PostgreSQL で、id が自動採番されるテーブルにレコードを挿入してからロールバックすると、レコードは消えるのに番号は元に戻らないと習いました。なぜ番号も戻してくれないんですか。番号が飛んだままでも問題ないのでしょうか？

  • PostgreSQL の自動採番って、現状でどこまで番号を使用したかを、どこかに保存しているんですか。テーブルの id の最大値を毎回調べているのでしょうか。それとも、テーブルとは別の場所で管理しているんですか。実際にどこまで進んでいるか、自分で調べることはできますか？

  • PostgreSQL の自動採番を、練習前の番号にリセットしたいです。次に付ける番号を自分で指定する方法はありますか。すでにレコードが入っているテーブルでも、1 から振り直して大丈夫なのでしょうか？
